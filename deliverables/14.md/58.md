## 三、必须修正的三点

### 1. “val_thr 从 GenImageSD14 划 1,500–2,000”不能解决 CoCoGlide

如果协议仍是**逐族阈值**，把 SD14 划进 val_thr 只会给出 **SD14 的阈值**，不会给 **CoCoGlide** 的阈值。

可选修法（三选一，必须预注册）：

| 方案 | 结果 |
|---|---|
| A. 给 CoCoGlide 单独划 val_thr 样本 | 才能真正给 CoCoGlide 冻结阈值 |
| B. 显式定义“扩散族共享阈值” | 用 SD14 等 val 样本拟合，但必须标注“跨生成器共享，非逐族” |
| C. CoCoGlide 只报 AUC/AP | 不报 ACC/bAcc，因其无冻结阈值 |

不能默认用 SD14 阈值顶 CoCoGlide。

### 2. 三个引用数字未在本地材料中定位

| DeepSeek 引用 | 本地核查 |
|---|---|
| “12 族宏 AUC 0.9761” | 未在 `456` / `472v4` / 已查交付物中找到；采纳前要给 json + md5 |
| “thr 0.0201 是 test 搜出来却标 false” | 未定位到具体产物；但结构冲突成立，需查 test 逐族 json |
| “我们现在那个 0.5550” | 本地 `0.5550` 见于 COVERAGE external 的 F1（`deliverables/115`），不是 cls_v2 共享池 macro F1；引用前必须核对来源 |

### 3. SHA256 泄漏检查不必按“519,935 张重算 18 分钟”执行

manifest 行里已经带 `sha256` / `source_key` 字段（`manifest_val_thr_slice12k.jsonl` 实证）。  
正确做法：**先用现成字段做 train×test / 跨 split 交集；只对缺字段的行补哈希**。

## 四、我建议的执行顺序

1. **先出三份逐族表**（val_thr / test / val_sel）：  
   `族 | n_real | n_fake | AUC | bAcc | r_acc | f_acc | thr | thr_source | thr_searched | F1(pooled或平衡口径)`  
   目的是立刻暴露 `progan` / `CoCoGlide` 的错位。
2. **审计 test 的阈值来源**：逐族核对 `thr_source` 与 `thr_searched`，确认 456/472v4 的“17/17 零搜索”是否成立。
3. **跑泄漏交集**：用现有 `sha256` / `source_key`，不重算全库哈希。
4. **再决定 v16 怎么划**：尤其是 CoCoGlide 是否有可划入 val_thr 的非 test 样本；没有就走方案 B/C。
5. **QF 全量审计后置**：先泄漏与阈值，后 QF。

**一句话**：DeepSeek 的“先查数据、test 不补、val_sel 改规则、F1 分口径”我同意；但 **val_thr 补 SD14 ≠ 解决 CoCoGlide**，且 **test 阈值来源与 val_thr 族表存在结构性冲突，必须先审**。
