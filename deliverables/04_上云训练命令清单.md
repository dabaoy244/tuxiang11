## 2. 控制台：开机前必做的三件事

### ① 立刻关机 → 切「无卡模式」开机

控制台 →【关机】→ 等状态变「已关机」→【开机】→ 计费方式选 **无卡模式**。

> 限制：部分区域无卡模式只有 2 核 4G；**同一账号同时只能开一个无卡实例**。

### ② 充值

看余额能不能覆盖**一次完整实验**：建议 **¥200**（75–120 卡时 ≈ ¥150–200 + 数据盘月费）。

### ③ 查数据盘（唯一可能推翻整台机器的事实）

控制台 →【实例详情】→ 看 **数据盘容量** 与 **可扩容上限**。

| 路线 | 峰值占用 | 能出什么 |
|---|---|---|
| 只下 test / val / CASIA（不下 train） | ≈ **25 GB** | 泛化表、定位实验；**出不了正式训练指标** |
| **train 只解 4 类（推荐）** | ≈ **89 GB** | 完整三阶段训练 |
| train 全 20 类 | ≈ **145 GB** | 同上，但**多花 56GB 换来零收益** |

**需要 ≥150GB，推荐 200–250GB。**

> ★ **为什么"只解 4 类"不亏**：`configs/default.yaml` 写着 `max_samples: 40000` ——
> **盘上是 4 类（14.4 万张）还是 20 类（72 万张），训练实际都只取 4 万张。**
> 论文里注明训练集范围即可。兑现承诺再扩容（数据盘按**当天最高容量**计费）。
>
> ⚠️ **若"可扩容上限"显示 0GB**：这台机器永远扩不了 → **现在释放、换一台可扩容的**。
> 这比显卡型号更是硬否决项。

## 4. 无卡模式阶段（¥0.1/时，约 ¥5 干完）

**一次性按顺序跑这 6 条**（第 0 条随时可插）：

```bash
bash scripts/cloud_autodl.sh status    # 只读：我现在走到哪了 / 下一步跑哪个 stage（随时可跑）
bash scripts/cloud_autodl.sh doctor    # 体检：GPU / torch 是否 CUDA 版 / 磁盘 / 依赖 / 解包位置 / 旧副本
bash scripts/cloud_autodl.sh install   # 装云端依赖子集 + torch·numpy·transformers 互斥自检与自动修复
bash scripts/cloud_autodl.sh clip      # 取真 CLIP-ViT-B/16 权重（先查版本互斥，避免白试两个源）
bash scripts/cloud_autodl.sh data      # 下 val / test / CASIA / train 4 类（约 90GB，最耗时）
bash scripts/cloud_autodl.sh verify    # 数据体检 + 全量自检 + 数据能否吃进去 + 骨干真伪
```

每个 stage 都可**单独重跑**，不会互相破坏。

> ⚠️ **例外：`data` 别随便重跑。** train 的 7 个分卷在解压成功后会**被自动删掉**（省 70GB），
> 重跑就会**重新下载那 70GB**。先判断：`ls /root/autodl-tmp/data/_downloads/progan_train.7z.00*`
> 若提示 "No such file"，说明分卷已删、数据已在盘上 → **别跑 `data`**，直接跑 `verify`。
> （修复版已加「已解压就不重下」的判据；若你用的是旧包，这条尤其要记住。）

## 5.5 ★ 起跑前必做：先跑速度探针（2026-09-26 实测：stage2 比 stage1 慢约 14 倍）

> 云上实测（RTX 4090，17:21→17:29）：stage2 的 `iter` 行是 **1.47 s/iter**
> （`iter 150/2875 … 238.6s` → `iter 300/2875 … 458.5s`），折合 **约 70 分钟/轮**；
> 而 stage1 约 0.10~0.19 s/iter（20 轮 ≈ 100 分钟）。
> **同一台机器、同一份数据，只差"loc 支路是否参与反传"，就慢了十几倍。**
> 按结构算，stage2 最多只该慢 1.5~2 倍（额外的是 224×224 上的 refine/edge 卷积）。
> 换句话说这不是"stage2 本来就重"，而极可能是**卷积反向掉进了慢路径** ——
> 启动日志里恰好躺着一条
> `UserWarning: Plan failed with a cudnnException … CUDNN_STATUS_NOT_SUPPORTED`。
> 不查就直跑完剩下的 50 轮 = **约 58 小时 ≈ ¥110**（原估 5~7 小时 / ¥14）。

**探针：2 条命令，各 1~3 分钟。** 行为与正式训练完全一致，只是把 batch 数压到 20：

```bash
cd /root/autodl-tmp/vibnet-forgery-detector
PROBE="--config configs/default.yaml --device cuda --amp --workers 16 \
  --data-root /root/autodl-tmp/data/Datasets --epochs-scale 0.05 --limit-batches 20"

python scripts/train.py $PROBE --tag probe_on  --out-dir outputs/probe_on  --cudnn on  | tee outputs/probe_on.txt
python scripts/train.py $PROBE --tag probe_off --out-dir outputs/probe_off --cudnn off | tee outputs/probe_off.txt

grep -E "iter |cuDNN" outputs/probe_on.txt  | tail -12
grep -E "iter |cuDNN" outputs/probe_off.txt | tail -12
```

**怎么读**：每个阶段各有自己的 `iter` 行；行尾秒数是**本轮累计**，
相邻两行差值 ÷ 5 = 每 batch 秒数。

| 结果 | 结论 | 下一步 |
|---|---|---|
| `probe_off` 明显快（如 1.47 s → 0.2 s） | 反向卷积确实在 cuDNN 慢路径里 | 正式跑加前缀 `CUDNN=off` |
| 两条一样慢 | 与 cuDNN 无关 | 再加一条 `--amp-dtype float16` 对照；仍一样就把两组 `iter` 行发我 |
| 两条都快、且与 stage1 同量级 | 之前的异常是临时的（机器被共享 / 降频） | 直接正式跑 |

#### 6.0.1 中断后如何重跑（★ 2026-09-27 真实场景）

> 2026-09-27 23:15 启动的那次一条龙链路，跑到约 37 分钟（stage1 第 4~5 轮附近）时被**手动关机**打断。
> 这种"中途断掉"是常态（误操作、按量计费余额不足、实例被回收），重跑清单如下。

```bash
# ① 本地：把最新的 run_all_pipeline.sh 传上云（脚本改过就必须重传，否则跑的是旧行为）
scp -P <端口> scripts/run_all_pipeline.sh root@<host>:/root/autodl-tmp/vibnet-forgery-detector/scripts/

# ② 云端：确认数据软链；归档被中断那次的权重（日志脚本会自己归档，权重不会）

    bash scripts/run_all_pipeline.sh \
    > outputs/cloud_runall_launch.log 2>&1 < /dev/null &
```

**要不要"续训"？不用。** 三条理由：

1. **损失极小**：本次中断时 stage1 只跑了约 5/20 轮，占整条链路（约 10 小时）不到 6%；
   全量重跑只多花约 30~40 分钟，比人工核对断点更省事，且结果一定干净。
2. **`--resume` 的语义容易踩空**：它**只加载权重、不推进阶段与轮次**（见 `scripts/train.py --help`）。
   要真续训必须同时给 `--start-stage`，还要人工确认 optimizer / scheduler / `global_epoch`
   计数是否都被正确恢复 —— 任何一处没恢复，都会得到一个"看着跑完了、口径却不一致"的权重。
3. **与项目结论一致**：`VERSION.txt` §[10] 已写明，本版口径下**应当从 stage1 全量重跑**。

> ⚠️ 关机重启后 `outputs/` 与 `checkpoints/` **都还在**（AutoDL 关机保留数据盘），
> 所以上一次的日志不会被自动清掉。`run_all_pipeline.sh` 启动时会先把旧的
> `gpu_train_log.txt` / `gpu_eval_log.txt` / `RUN_REPORT.txt` 归档到 `outputs/_archive/`，
> 避免两次运行的 iter/epoch 连在同一份日志里跳变。

## 附录 A · CLIP 权重怎么取（直达链接）

### A.0 先想清楚：这个权重是放到**云实例**上的，不是"发给别人"的

它落在云实例里这个路径：

```
/root/autodl-tmp/vibnet-forgery-detector/pretrained/clip-vit-base-patch16/
```

而**正常情况下根本不需要你手动下** —— `clip` 那条命令会在云上下（云有 AutoDL 学术加速，机房带宽比家里快得多）：

```bash
bash scripts/cloud_autodl.sh clip     # 先跑这个。成功了就不用看下面
```

**只有当它两个源都失败**、且已排除"版本互斥"这个假失败时（见 §4 的 CHECK 点），才需要手动下。

> ⚠️ **不要在生产路径上"本地下载再上传"**：`pytorch_model.bin` 有 **571 MB**，
> 从家里上传比云端机房拉取慢得多。本地下载只作**最后手段**（见 A.4）。

### A.1 三个源（都可直连，无需 token、无需登录）

| 源 | 地址 | 备注 |
|---|---|---|
| HuggingFace 官方 | `https://huggingface.co/openai/clip-vit-base-patch16` | 部分网络不可达 |
| **hf-mirror（国内镜像，推荐）** | `https://hf-mirror.com/openai/clip-vit-base-patch16` | 项目脚本自带这个源 |
| **魔搭 ModelScope** | `https://www.modelscope.cn/models/openai-mirror/clip-vit-base-patch16` | 国内速度稳 |

### A.2 真正必需的只有 3 个文件（其余别下）

| 文件 | 大小 | 要吗 |
|---|---|---|
| `config.json` | **4.1 KB** | ✅ 必需 |
| `pytorch_model.bin` | **571 MB**（598,641,023 字节） | ✅ 必需（权重本体） |

| `flax_model.msgpack` | **571 MB** | ❌ Flax/JAX 用的，**下了纯浪费一倍体积** |

> 📌 该仓库**没有 `model.safetensors`**，只有 `pytorch_model.bin`。别去找 safetensors。

**直达下载链接**（把 `hf-mirror.com` 换成 `huggingface.co` 即为官方）：

```

https://hf-mirror.com/openai/clip-vit-base-patch16/resolve/main/pytorch_model.bin
https://hf-mirror.com/openai/clip-vit-base-patch16/resolve/main/preprocessor_config.json
```
