## 1. 空域分支的维度描述前后不一致（公式 (1)(3) 与 1.3(3) 冲突）

**问题**

- 公式 (1)(3) 把空域特征写成**向量**：`φ(x) ∈ R^768`、`F_local ∈ R^128`、`F_spa ∈ R^896`；
- 但 1.3(3) 又说"定位支路直接使用……**512 维空频融合特征图（尺寸为 14×14×512）**"。

向量（1 维）和特征图（3 维，14×14×512）**不可能同时成立**。
更关键的是：`Concat(φ(x), F_local)` 得到的是一个 896 维向量，
**通道拼接后再做 1×1 卷积，空间分辨率是 1×1，不可能变成 14×14**。
如果照公式原样实现，定位支路的输入会是 1×1×512，Mobile-UNetv2 的上采样没有任何空间信息可恢复，
**mIoU 会低到接近 0**。

**本仓库的修正实现（`src/models/spatial_branch.py`）**

| 量 | 公式写法 | 实现写法 | 说明 |
|---|---|---|---|
| φ(x) | R^768 | `(B, 768)` | 保留 CLIP 的 **CLS token**，与公式 (1) 一致，用于整图判别 |
| 空域空间特征 | —— | `(B, 768, 14, 14)` | 用 **patch token**（去掉 CLS）重排得到，与 224/16=14 对应 |
| F_local | R^128 | `(B, 128, 14, 14)` | 3 层深度可分离卷积输出后池化到 14×14（GAP 即得 R^128，与公式 (2) 一致） |
| F_spa | R^896 | `(B, 896, 14, 14)` | 通道拼接；对其做 GAP 就得到公式 (3) 的 896 维向量 |

**答辩时怎么答**

> "公式 (1)(3) 给出的是从特征图抽取的**全局向量表示**（用于分类支路的语义描述）；
> 而定位支路必须保留 14×14 的空间分辨率。因此实现时我们同时保留两种形式：
> CLS token 作为 768 维全局语义向量，patch token 重排为 14×14×768 的空间特征图，
> 与局部纹理特征在通道维拼接得到 14×14×896 的 F_spa。
> 对 F_spa 做全局平均池化即还原为 896 维向量。"

**建议在论文里改的写法**：把公式 (3) 补一句"（记为特征图形式为 14×14×896）"，
或直接写成 `F_spa ∈ R^{896×14×14}`。**这是必须改的**，否则审稿人一眼看出维度矛盾。

## 2. "梯度停止层"在双兄弟头结构下前向是恒等映射（等于没做）

**问题**

申报书 1.3(1) 描述的三条性质：
> ① 分类支路的梯度仅回传至 VIB 模块和 F_fusion，不会回传至定位支路
> ② 定位支路的梯度仅回传至定位头和 F_fusion，不会回传至分类支路
> ③ F_fusion 同时接收两条支路的梯度

**在"共享 F_fusion + 两个兄弟头"的朴素结构下，①②③ 是自动成立的** ——
分类头与定位头之间没有计算图连线，梯度物理上不可能跨支路串扰。
也就是说：**把 GS 实现成恒等映射，模型的数学行为和没加它完全一样。**

如果论文里写"引入梯度停止层实现梯度隔离，从根本上解决任务间干扰问题"，
但没有解释 GS 到底挡住了哪条梯度路径，**审稿人一定会问："你挡的是哪条路径？"**
答不上来就只能撤回这句话。

**本仓库的处理（`src/models/gradient_stop.py`）**

实现为**可配置的 autograd 门控**，两种语义：

| 配置 | 语义 | 什么时候用 |
|---|---|---|
| `gs_stop_cls: false`（默认） | 恒等映射，前向与反向都无影响 | 与申报书描述的前向行为一致；在计算图中显式标注解耦点，便于可视化 |
| `gs_stop_cls: true` | **阻断分类支路梯度回传到 F_fusion** | 共享特征完全由定位任务驱动（定位精度优先） |
| `gs_stop_loc: true` | **阻断定位支路梯度回传到 F_fusion** | 共享特征完全由分类任务驱动（跨模型泛化优先） |

**关键点：** 打开 `true` 之后，**共享特征的优化目标被明确限定为单任务**，
这与 PCGrad / GradNorm 属于同一类"缓解多任务梯度冲突"的思路，但**零额外计算开销**，
并且能在消融表里观察到真实的指标差异 —— 这时"梯度隔离"才是有内容的。

**答辩时怎么答**

> "在共享主干 + 双头结构下，两条支路之间本无计算图连接，因此我们把梯度隔离
> 实现为**对共享特征 F_fusion 的任务级门控**：在联合微调阶段，通过梯度停止层
> 控制共享特征由哪个任务驱动，从而显式地消除梯度冲突。
> 消融实验（no_grad_stop）证明该机制带来了 X% 的提升。"

**建议在论文里改的写法**：把 1.3(1) 的表述从"阻止梯度在两条支路间回传"
改为"通过对共享空频融合特征施加任务级梯度门控，将共享特征的优化目标限定为主任务，
缓解多任务梯度冲突"。**这是必须改的**。

## 3. 模型体积 ≤120MB 与 CLIP-ViT-B/16 骨干不兼容（最硬的指标冲突）

**问题**

申报书 3.1 与 6.3 都要求 **模型体积 ≤120MB**，同时 1.1(1) 又要求用
**CLIP-ViT-B/16** 作为骨干。这两件事**在 FP32 下不可能同时成立**：

| 组件 | 参数量 | FP32 体积 |
|---|---|---|
| CLIP-ViT-B/16 视觉塔 | ≈86.2 M | ≈344 MB |
| Mobile-UNetv2 定位头 | ≈3.7 M | ≈14.8 MB |
| 频域分支 + CS-CAM + VIB + 分类头 | ≈0.9 M | ≈3.6 MB |
| **合计** | **≈90.8 M** | **≈363 MB** |

（本仓库用轻量兜底骨干时实测：总参数量 33.84 M、FP32 135.4 MB、**仍然超标**。
换成真正的 CLIP 后是 ~363MB。）

**三条可行出路（按性价比排序）**

### 出路 A：INT8 训练后量化（**强烈推荐**）

```bash
python -m src.deploy.optimize_openvino --onnx deploy/vibnet_simplified.onnx --int8
```
- 体积：86M × 1 byte ≈ **86 MB**，加其他模块约 **90 MB**，**达标**；
- 副作用：Intel CPU 上吞吐通常还能再涨 1.5~2×；
- 代价：需要 100~300 张校准图（真实/伪造各半最佳），且 ACC 通常掉 0.3~1 个点。
- **申报书 3.1 已经写了 OpenVINO 优化，把 NNCF INT8 量化补进去非常自然。**

### 出路 B：换轻量 CLIP 变体

| 骨干 | 视觉塔参数量 | FP32 体积 |
|---|---|---|
| MobileCLIP-S2 | ≈35 M | ≈140 MB |
| TinyCLIP-ViT-8M | ≈8 M | ≈32 MB |
| ViT-B/32（CLIP 原版） | ≈88 M | ≈352 MB（**没用**） |

换成 `TinyCLIP` 或 `MobileCLIP` 后 FP32 就能达标，但需要重新验证跨模型泛化性是否下降。
本仓库支持通过 `model.spatial.clip_pretrained` 直接换骨干。

### 出路 C：知识蒸馏

用 CLIP-ViT-B/16 当教师，蒸馏到一个 MobileNetV3 / TinyViT 学生骨干（10~20M 参数），
兼顾泛化性与轻量。工作量大（多一个月），但如果要发核心期刊，这是**最能讲故事**的方案。

**答辩时怎么答**

> "体积指标我们是按**部署形态**核算的：训练用 FP32，部署时经 OpenVINO NNCF
> 做 INT8 训练后量化，最终 IR 模型 XX MB，满足 ≤120MB 的端侧要求；
> 同时 CPU 推理速度从 FP32 的 X 张/秒提升到 Y 张/秒。"

**务必在中期检查前把这条说清楚**，别等到结题才发现指标自相矛盾。

## 4. 频域分支"频域信息利用率提升 100%"的表述不严谨

**问题**：从"仅用幅值（128 维）"到"幅值+相位（256 维）"，
特征**维度**翻倍 ✓，但说"信息利用率提升 100%"是把**维度当信息量**。

**怎么改**：改成可验证的表述——

> "在消融实验中，引入相位支路后 ForenSynths 检测准确率提升 X%（见消融表），
> 说明相位谱所包含的结构信息对扩散模型伪造痕迹的判别具有独立贡献。"

**并且**：申报书 1.1(2) 里"相位信息对扩散模型生成图像的检测贡献是幅值信息的 1.7 倍"
这句话，**必须标注出处**（哪篇文献、什么数据集、什么指标下测出的 1.7）。
如果是自己测的，就写清楚实验设置。**凭空出现的 1.7 倍是审稿雷区。**

## 5. 消融实验说"逐步移除关键模块"，但没写要重新训练

**问题**：消融实验的**唯一合法做法**是每个配置**独立重新训练**。
如果只加载同一个 checkpoint 再关掉某个模块做推理，得到的是
"该模块对**推理**有影响"，**不能**说明"该模块对训练/泛化有贡献"。

**影响**：这是给审稿人送人头。7 个消融项 × 每项完整训练 → **至少两周连续算力**，
必须提前排算力。

**本仓库的处理**：`src/evaluation/ablation.py` 提供 `--mode eval`（流程自检，会打印警告）
和 `--mode train`（正式实验，每项独立训练）。

**⚠ 当前状态（2026-09-29 核实）**：**7 条消融臂一次都没训练过。**
`scripts/run_ablation.py` 的 `ARMS` 只定义了 `random` / `pretrained` 两条（骨干权重消融），
`outputs/ablation_*` 下只有那两条的产物；全仓搜索 `no_cross_attention` / `no_vib` /
`no_edge` 的产物只命中权重文件（里面存的是 config，不是结果）。
⇒ 因此**本文档第 2 条的答辩话术"消融实验（no_grad_stop）证明该机制带来了 X% 的提升"
目前无数据支持**，必须先把该臂跑出来，或把话术改为"该机制已在代码中实现并接入训练"。
同理，`docs/13` 与论文里**任何"消融证明模块有效"的句子在跑完消融前都不能写**。

**建议**：如果算力紧张，可以把消融实验的轮数统一降到 40 轮
（`--epochs-scale 0.6`），并在论文里注明"消融实验采用 40 轮设置"。
优先级：`no_cross_attention` / `no_vib` / `no_edge` 三条（对应三个创新点）> 其余。

## 6. ForenSynths"10 万张"与实际可获取规模不符

**问题**：申报书写 ForenSynths "共计 10 万张"。实际上 ForenSynths 的数据量取决于
你取哪些生成器：`progan` 单独约 8 万，加上 `cyclegan / biggan / stargan / gauGAN /
styleGAN / diffusion` 等才是申报书说的"跨生成模型"规模，**总计数十万张**。
更关键的是：**ForenSynths 需要向作者申请**（CNNDetection 仓库），
**存在拿不到或拿到的是子集的风险**。

**应对**：
1. **尽早申请**（6 月第一周就发邮件），不要等到 8 月；
2. 备选数据源：
   - 自己用 SD / SDXL / Midjourney / DALL·E 生成（成本低、可控、还能造"未知生成器"测试集）；
   - `GenImage`（更大更全，但更大）；
   - `DeepFake / DeeperForensics`（人脸域，可作为补充实验）。
3. **自己生成的数据务必记录 prompt、模型版本、随机种子**，论文里要能复现。

**同时注意**：跨生成模型泛化的**核心是"留出未知生成器"**。
训练时用 progan + styleGAN + cycleGAN，测试时**额外留出 diffusion 类**，
这才是能证明泛化性的实验设计。如果训练集里已经有 diffusion，那 91% 就说明不了跨模型泛化。

## 7. "三阶段训练（分类预训练→定位预训练→联合微调）"与"梯度隔离"有内在矛盾，需要解释

**问题**：

- 阶段一分类预训练时，定位支路被冻结 → 分类梯度**会**更新共享特征 `F_fusion`；
- 阶段二定位预训练时，分类支路被冻结 → 定位梯度**会**更新共享特征 `F_fusion`；
- 阶段三两者都解冻 → 两个任务的梯度**同时**更新 `F_fusion`。

如果此时 GS 仍然是恒等映射，那么"梯度隔离"在阶段三就形同虚设；
而如果 GS 在阶段三真的阻断了一条，那"F_fusion 同时接收两条支路的梯度"就又不成立。

**这是逻辑上必须自洽的一点**，评审一定会问："你到底隔离了没有？"

**建议的统一说法（也是本仓库的实现）**：

> 梯度隔离机制的作用是**在共享特征层面把两个任务的优化目标解耦**：
> - 阶段一/二通过**参数冻结**实现硬隔离（另一支路完全不参与）；
> - 阶段三提供可选的**任务级梯度门控**：默认关闭（两支路协同优化共享特征），
>   当定位与分类出现明显梯度冲突时（表现为两个任务的验证指标交替恶化），
>   打开门控让共享特征由主任务驱动。
> 消融实验给出的结论是：……

**建议在论文里新增一张表**：三种 GS 配置（都关 / 只关分类 / 只关定位）
在 ForenSynths ACC 和 CASIAv2 mIoU 上的对比。**有了这张表，"梯度隔离"这一节就立住了。**

## 8. "通道-空间**交叉**注意力"名与实不符（模块里没有跨支路交互）

**问题**：1.1(3) 把融合模块叫「**交叉**注意力（cross-attention）」，
但申报书自己给的公式 (15)(16)(17) 描述的是：

```
F_spa''  = F_spa'  * CA(F_spa')  * SA(F_spa')      (15)   ← 只用到 F_spa' 自己
F_freq'' = F_freq' * CA(F_freq') * SA(F_freq')     (16)   ← 只用到 F_freq' 自己
F_fusion = F_spa'' + F_freq''                      (17)   ← 相加
```

**两条支路之间没有任何交互**，也没有 Q/K/V。这在文献里的名字是
**CBAM（通道注意力 + 空间注意力）**，不是 cross-attention。
`src/models/cs_cam.py` 严格按公式 (13)~(17) 实现（含 7×7 空间卷积、降维比 r=16），
所以**代码没错，是名字错了**。

**影响**：答辩/审稿一问「你的交叉注意力里 Q、K、V 分别取自哪里？」就答不上来；
而且"交叉注意力"是比 CBAM 更强的创新性声明，名实不符属于**夸大**，风险不低。

**两条处理办法**：

| 办法 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 改名 + 改述为「**通道-空间双重注意力融合（CBAM 式）**」，方法章节明确写"两支路**独立**做注意力后逐元素相加，不做跨支路交互" | 同步改本文档与 `docs/11` 的修订说明；不影响任何考核点 |
| B | 真做成跨支路注意力（一支路出 Q，另一支路出 K/V） | 要改模型 + 重训，且与公式 (13)~(17) 不再一致 |

**答辩时怎么答（选 A 时的口径）**：

> "该模块由通道注意力与空间注意力串联构成，对空域、频域两支特征**各自**做
> 通道-空间双重加权后再相加融合。申报书里'交叉'一词指的是
> '通道维与空间维的交叉建模'，不是 transformer 意义上的跨序列交叉注意力
> —— 这一点我们在论文中已明确表述为 CBAM 式双注意力。"

## 一句话总结

申报书整体技术路线是**成立且合理的**，主要问题集中在三类：

1. **维度/结构描述不一致**（第 1 条）—— 不改会导致定位支路失效；
2. **机制描述与实际数学行为不符**（第 2、7、8 条）—— 不改会在答辩时被问穿；
3. **指标之间互相矛盾**（第 3 条）—— 不改会在结题时发现达不到；
