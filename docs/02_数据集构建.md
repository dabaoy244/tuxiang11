# 02 · 数据集获取与构建

## 一、三套数据集的定位（先搞清楚，别混用）

| 数据集 | 任务 | 有无像素掩码 | 规模 | 本项目用途 |
|---|---|---|---|---|
| **ForenSynths** | 整图真伪（GAN/扩散/自回归） | ❌ 无 | 训练约 72 万张（ProGAN 20 类） | 训练分类支路的**核心**，评测跨生成模型泛化性 |
| **CASIA v2** | 传统篡改（拼接/复制移动/修图） | ✅ 有 | **7491 真 + 5123 篡改（合计 12614）**<br>其中篡改 = 3274 复制移动 + 1849 拼接 | 训练定位支路，评测定位 mIoU |
| **COVERAGE** | 复制移动细粒度定位 | ✅ 有 | 100 真 + 100 篡改 | 评测细粒度定位（更严格） |

> ⚠️ **2026-09-18 更正**：本表原先写「CASIA v2 = 5123 真 + 3285 篡改」，**是错的**。
> 经 Springer / IEEE 多篇文献交叉核对，CASIA v2.0 的权威构成是
> **12614 张 = 7491 真实 + 5123 篡改**（篡改再细分为 3274 复制移动 + 1849 拼接）。
> 旧写法把「5123」错标成了真实图数量，又把 3274 抄成了 3285。引用时以本节为准——
> 论文里写错数据集规模是很显眼的失分点。
> 常见划分比例：80% 训练（5993 真 + 4098 伪）/ 20% 测试（1498 真 + 1025 伪）。

**必须分清的两件事：**

1. **ForenSynths 没有像素掩码。** 它是"整张图是真是假"，不是"哪里被改了"。
   混进批次时必须用 `mask_valid` 过滤掉定位损失，否则补零掩码会把定位支路
   教成"全部输出真实"。本仓库的 `collate_multitask` + `MultiTaskLoss(mask_valid=...)`
   已经处理了这件事。
2. **"跨生成模型泛化"的关键是留出未知生成器。** 训练时用的生成器
   和测试时用的生成器**必须不同**，否则 91% 的准确率说明不了泛化性。
   建议：训练用 `progan / styleGAN / cycleGAN`，**测试用 diffusion 类（如 guided / ldm / glide）**。

> 📌 **训练集的两个实测事实（2026.09.19，直接从分卷读出，未解压）**
> 1. **结构是「7z(Copy，零压缩) 包着一个 zip」**（`Method = Copy`），内层
>    `progan_train.zip` 74.9 GB。所以"先用 7z 解出 zip、再解 zip"这条常规路径的
>    磁盘峰值 = 74.9 + 74.9 = **149.8 GB** —— 本机 D 盘 113.5 GB 可用，**中途必然写满**。
> 2. **内层 zip 是 ZIP64**（经典 EOCD 里的中央目录偏移是 `0xFFFFFFFF` 哨兵值）。
>    本项目的 `fetch_datasets.py` 因此改为**分卷直读**：把 7 个分卷在逻辑上拼成一个
>    可 seek 的只读流，裁到内层 zip 那一段直接交给 `zipfile`，**零中间产物**，
>    峰值只剩解压产物（**69.8 GB** ≤ 113.5 GB）。
>
> 逐类清点（`python scripts/fetch_datasets.py --split train --list-train`，零磁盘开销）：
> 20 个类各 **36006 张**（`boat` 36005），解压后合计 **69.8 GB**：
> `airplane 2.8G / bicycle 3.9G / bird 3.5G / boat 3.5G / bottle 2.7G / bus 3.6G /
> car 3.5G / cat 3.5G / chair 3.0G / cow 4.0G / diningtable 3.6G / dog 3.7G /
> horse 3.9G / motorbike 3.9G / person 3.3G / pottedplant 4.1G / sheep 4.2G /
> sofa 3.0G / train 3.7G / tvmonitor 2.6G`。

- **本项目下载工具**（已实现，支持多镜像自动切换 / 断点续传 / 选择性解压）：
  ```bash
  # 先下最小的两个（1.6 GB），用于快速跑通真实数据
  python scripts/fetch_datasets.py --split val progan_test
  # 跨生成器泛化测试集（18.7 GB，挂夜）
  python scripts/fetch_datasets.py --split test
  # 正式训练集（74.9 GB）。**先看有哪些类**（零磁盘开销，秒级）：
  python scripts/fetch_datasets.py --split train --list-train
  # 只解几个类最省磁盘（该选项此前对训练集不生效，2026.09.19 已修，见 docs/08 D31）：
  python scripts/fetch_datasets.py --split train --classes car cat chair horse
  # 全量解压（解压产物 69.8 GB；脚本会先做精确空间预检，不足直接拒绝开工）
  python scripts/fetch_datasets.py --split train
  # 国内镜像（huggingface.co 慢时）
  python scripts/fetch_datasets.py --split val --mirror hf-mirror
  # 只想下压缩包、稍后手动解压（省解压期的磁盘峰值）
  python scripts/fetch_datasets.py --split train --no-extract
  ```
  > **本机现状（2026.09.19）**：7 卷已下载并通过**结构级只读验证**
  > （字节数与远端逐字节相等；`--list-train` 在真实分卷上成功解析出
  > 720119 条目 / 20 类，与损失前记录一致）。但 D 盘重下后只剩 **44 GB**，
  > **小于全量解压所需的 69.8 GB** —— 所以**本机不要再解压 train**，
  > 训练集只以 7 卷形态保存，上云时传 7 卷、在云端解压（见 `docs/08` D34、
  > `docs/15`）。本机要跑训练集相关实验，用 `--classes` 解 1–2 个类即可。

  > ⚠️ **解压前必看**：默认**解压成功后删除压缩包**（省 74.9 GB）。删除有三道闸门：
  > ① 类名零命中 → 直接终止并保留压缩包；② 解压项数少于计划、或**一个文件都没解出来**
  > → 一律判失败、保留压缩包；③ 解压路径不做空间预检时不会开工。
  > 这三道闸门是被一次**真实的 74.9 GB 数据损失**逼出来的（`docs/08` D32）——
  > 当时类名写错，脚本"成功解压 20 个空目录"并通过完整性校验，随后删掉了 7 个分卷。
  > 需要保底可加 `--keep-archive`。
  > 自检：`python scripts/fetch_datasets.py --self-test`（18 项，已并入 `scripts/smoke_test.py`）。
  > **`--mirror auto`（默认）会在 `huggingface.co` 被阻断时自动切到 `hf-mirror.com`，
  > 并做指数退避重试（15 s → 300 s，最多 12 次），每轮重试都带断点续传。**
  > 这是被真实故障逼出来的：早期单镜像下载时，`huggingface.co` 被间歇性阻断，
  > 7 个分卷全部以 `SSL: UNEXPECTED_EOF_WHILE_READING` 失败。
  >
  > 下载期间想看任务死没死，用 `python scripts/check_status.py`（三证据交叉判定），
  > **不要**因为命令行出现 crashpad 的 `CreateFile: 0x2` 就以为失败了——那是 Git Bash 噪音。

  > 训练集是 7 卷 7z（`Method = Copy`，零压缩）**包着一个 zip**。本项目**不走**
  > "7z 解出中间 zip 再解 zip" 的常规路径，而是用 `SplitVolumeReader` 把 7 卷拼成
  > 一个可 seek 的只读流、裁到内层 zip 那一段直接交给 `zipfile`：
  > **零中间产物**，磁盘峰值 = 解压产物本身（69.8 GB），而非 7 卷 + 内层 zip + 产物（≈ 219 GB）。
  > 解压只依赖标准库 `zipfile`（**不需要** `7z` / `py7zr`）。

### 2.2 CASIA v2

- **规模（权威口径）**：12614 张 = 7491 真实 + 5123 篡改。
  **✅ 已实测核实**：文件级清点得到 **7491 个 `Au` + 5123 个 `Tp` + 5123 个 `Gt` = 17737 个文件 / 3.28 GB**，与权威口径完全吻合。
- **获取途径**：
  1. **✅ 本项目采用（已验证可用）**：ModelScope 勘误版
     `https://www.modelscope.cn/api/v1/datasets/Sunnyhaze/CASIAv2-Manipulated-image`
     —— 有掩码、有分页 API、国内直连速度可接受。**不需要注册、不需要发邮件。**
  2. GitHub 镜像 `https://github.com/namtpham/casia2groundtruth`（修正过标注，可作备选）；
  3. Kaggle 镜像（部分版本**不含 GT 掩码**，下载前先确认有没有 `Groundtruth/`，否则做不了定位）；
  4. 中科院自动化所官方站点（需注册，流程慢，非必要不走）。
- **本项目下载工具（已实现并跑通）**：
  ```bash
  # 下载（16 线程）→ 自动整理成 {train,val,test}/{image,mask}/ 三路划分
  python scripts/fetch_tamper_datasets.py --workers 16
  # 只下载不整理 / 只整理不下载 / 只检查
  python scripts/fetch_tamper_datasets.py --download-only
  python scripts/fetch_tamper_datasets.py --organize-only
  python scripts/fetch_tamper_datasets.py --check
  ```
  脚本的三个关键设计（都是被坑出来的）：
  - **服务端分页**：文件树 API 单页上限 3000，必须翻页，否则 17737 个文件只拿到 3000 个；
  - **`.part` 原子落盘**：先写临时文件再 `os.replace`，中断不会留下半截文件；
  - **真实图补黑掩码**：7491 张真实图原本没有掩码，补全黑掩码后定位支路才能用
    `mask_valid` 把它们正确过滤掉。

- 原始结构（ModelScope 版）：
  ```
  CASIAv2/
  ├── Au/          Au_xxx.jpg                     （7491 张真实图）
  ├── Tp/          Tp_D_CND_M_N_xxx_NNNNN.tif     （5123 张篡改图）
  └── Gt/          Tp_D_CND_M_N_xxx_NNNNN_gt.png  （5123 张掩码）
  ```

- **⚠️ 掩码索引规则（这里曾经有一个静默失效的严重 bug，务必看）**

  CASIA 的文件名形如 `Tp_D_CND_M_N_ani00018_sec00096_00138.tif`，
  掩码是 `..._00138_gt.png`。**早期代码用 `stem.split("_")[0]` 做索引键 —— 取第一个
  下划线之前永远是 `"Tp"`，于是 5123 个掩码全部塌缩成一个键，每张篡改图都匹配到
  同一张（错误的）掩码；而真实图的键 `"au"` 在掩码集里不存在，7491 张真实图被整个跳过。**

  结果是数据集里只剩「全部共用同一张掩码的篡改图」，**定位支路训的是垃圾，
  而且不报任何错**。已修复为「完整文件名（去扩展名，再去掉 `_gt` 后缀）」精确匹配，
  详见 `docs/08` 的 **C14 / C15**。

  修复后加载时会打印真实条数，**上云后第一件事就是核对这一行**：
  ```
  [TamperDataset] CASIAv2/train: 载入 10124 条（篡改 5123 / 真实 5001，掩码 5123 个）
  ```
  若"掩码 N 个"远小于"篡改 N 张"，说明掩码目录不完整，mIoU 必然偏 —— 不要往下跑。

## 三、规范化组织

```bash
# 1) 检查当前落盘情况
python scripts/prepare_datasets.py --root data/Datasets --check

# 2) 规范化（硬链接，不额外占磁盘；Windows 需 NTFS）
python scripts/prepare_datasets.py --root data/Datasets --organize --mode link

# 3) 生成 manifest（论文里"数据划分可复现"就靠它）
python scripts/prepare_datasets.py --root data/Datasets --manifest
```

规范化后的目标布局：

```
data/Datasets/
├── ForenSynths/
│   ├── train/{0_real,1_fake}/*.png
│   ├── val/{0_real,1_fake}/
│   └── test/{0_real,1_fake}/
├── CASIAv2/
│   ├── train/{image,mask}/
│   ├── val/{image,mask}/
│   └── test/{image,mask}/
├── COVERAGE/
│   ├── train/{image,mask}/
│   ├── val/{image,mask}/
│   └── test/{image,mask}/
└── manifest.json
```

**`--mode` 三个选项：**

| 模式 | 说明 | 什么时候用 |
|---|---|---|
| `link` | 硬链接（推荐） | 默认，不占额外磁盘，速度快 |
| `symlink` | 软链接 | 跨磁盘卷时用（硬链接不能跨卷） |
| `copy` | 物理复制 | 需要独立副本、或文件系统不支持链接时（会多占 200GB+） |

**划分比例：** 训练 80% / 验证 10% / 测试 10%，**按"是否篡改"分层抽样**，
保证各 split 的正负比例一致（脚本已实现）。

**真实图像没有掩码时：** 脚本会自动生成**全黑掩码**，
使每条样本都有 `mask` 字段，保证 DataLoader 逻辑统一（正样本为有内容的掩码）。

## 四、数据增强的取舍（很重要，容易做错）

### 训练时可以用的增强（温和型）

`src/data/transforms.py` 里只做了三类：

- 随机水平翻转（概率 0.5）
- 轻微旋转 ±5°（概率 0.3）
- 轻微色彩抖动（增益 0.95~1.05，概率 0.3）

### **不能**放进训练增强的（这些是"测试手段"，不是"训练手段"）

| 操作 | 为什么不能做训练增强 |
|---|---|
| JPEG 压缩 | 会把频域伪影一并抹掉，模型学到的是"JPEG 痕迹"而不是"伪造痕迹" |
| 强缩放 | 破坏生成模型上采样的周期性伪影 —— 这恰恰是频域分支的判别依据 |
| 强噪声 | 淹没噪声残差特征 |
| 随机裁剪 | 会切掉篡改区域，但掩码可能没同步更新，产生错误监督 |

> **申报书 3.3 的鲁棒性测试（JPEG/缩放/裁剪/旋转/加噪）是评测协议，不是训练增强。**
> 把这两件事混起来是最常见的实验设计错误之一，答辩会被直接问倒。
> 正确的做法是：**干净数据训练 → 后处理数据测试 → 报告指标下降率**（本仓库
> `src/evaluation/robustness.py` 就是按这个协议实现的）。

**`mask_valid` 是三阶段训练能跑通的关键：**
阶段一/二也要用同一份训练数据（不能为分类任务单独准备一套无掩码的数据），

平均里排除掉。

> **自己改代码时千万不要丢掉这个机制** —— 这是"定位支路输出全黑"问题的根因。

## 七、常见问题

| 现象 | 原因 | 解决 |
|---|---|---|
| `CASIAv2` 全部被标成 label=0 | 掩码文件名与图像名不匹配 | 索引逻辑在 `src/data/datasets.py::TamperDataset._mask_keys()`（**不是** `prepare_datasets.py`）。检查掩码是否带 `_gt` 后缀、是否与图像**完整文件名**能对上；加载时打印的「掩码 N 个」是关键线索 |
| `ForenSynths` 一条样本都没找到 | 官方层级是 `<generator>/<split>/`，不是 `<split>/` | `GenSynthsDataset` 已自动探测；若仍失败，检查是否存在 `0_real`/`1_fake` 目录名 |
| 硬链接报 `OSError: [WinError 17]` | 跨磁盘卷 | 改用 `--mode symlink` 或 `--mode copy` |
| 训练时显存爆 | ForenSynths 图像分辨率不一 | 统一缩放到 224（`data.image_size`）；极端长宽比的图像会被中心裁剪 |
| 磁盘不够 | 三套数据集总共 200~300GB | 用 `--mode link`；只保留训练需要的生成器子集 |
