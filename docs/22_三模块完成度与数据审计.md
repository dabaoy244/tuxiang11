## 二、三个模块逐个核

### 2.1 CS-CAM 通道-空间注意力融合

**实现**：`src/models/cs_cam.py`，对应申报书公式 (13)~(17)。

```
F_spa'  = Conv1x1(F_spa)                    (13)
F_freq' = Conv1x1(F_freq)                   (14)
F_spa'' = F_spa' * CA(F_spa') * SA(F_spa')  (15)
F_freq''= F_freq'* CA(F_freq')* SA(F_freq') (16)
F_fusion= F_spa'' + F_freq''                (17)
```

CA = CBAM 式通道注意力（GAP+GMP → 共享 MLP，降维比 r=16）；
SA = 空间注意力（沿通道轴 GAP+GMP → 拼接 → 7×7 卷积 → Sigmoid）。
参数量 **0.658 M**（`gpu_train_log.txt`），占整机 90.53 M 的 **0.73%**。
输入 `(B,896,14,14)` + `(B,256,14,14)` → 输出 `(B,512,14,14)`，与公式一致。

#### ⚠ 一处**必须主动说明**的口径问题：名与实不符

模块名（以及汇报话术）说的是 **「交叉注意力」**，但代码做的**不是**跨边支交叉注意力：

- 实现是 `a_spa = p_spa * CA(p_spa) * SA(p_spa)` 和 `a_freq = ...` —— **每条支路各自做 CBAM**，
  两支路之间**没有任何交互**，最后只是相加（公式 17）。
- 这在文献里叫 **CBAM / 双注意力**，不叫 cross-attention。
  交叉注意力（cross-attention）指一支路的 Query 去 attend 另一支路的 Key/Value，
  本模块没有 Q/K/V，也没有跨支路项。

**这不是 bug**——代码严格实现了申报书自己的公式 (13)~(17)；是**名字**与公式不符。
但答辩时如果被问"你的交叉注意力 Q、K、V 分别是什么"，会当场答不上来。
两个处理办法（任选）：

| 办法 | 做法 | 代价 |
|---|---|---|
| **A（推荐）** | 如实改名 + 改述：写成「**通道-空间双重注意力融合（CBAM 式）**」，并在方法章节明确"两支路**独立**做注意力后相加，不做跨支路交互" | 需要同步改 `docs/07`/`docs/11` 的修订说明，并确认不影响申报书考核点措辞 |
| B | 真做成跨分支注意力（`freq` 提 Q、`spa` 供 K/V） | 要改模型、重训，且与申报书公式 (13)~(17) 不再一致 |

> 这条目前 `docs/07 申报书待修正问题清单` 与 `docs/11 修订对照表` **都没有收录**，
> 建议补进去（`docs/07` 第 3 条只列了"空间注意力卷积核大小没写"）。

### 2.2 分层 VIB（β 退火 / KL 裁剪 / 梯度裁剪）

**实现**：`src/models/vib.py` + `src/engine/trainer.py`，对应公式 (18)~(26)。
参数量 **0.263 M**，占整机 0.29%。

「分层」名副其实：`vibnet.py` 里 VIB **只挂在分类支路**——
`f_cls_in = gs_cls(f_fusion) → vib → cls_head`；
定位支路拿的是 `gs_loc(f_fusion)`，**不经 VIB**。✓

#### (a) 三个机制的实测结果（`scripts/diag_vib_kl_gradnorm.py`，CPU，best.pt）

| 机制 | 设定 | 实测 | 判读 |
|---|---|---|---|
| **β 退火** | `β: 0 →(t=20..39 线性)→ 0.1` | 日志 100 行完整轨迹：t=19→0.0、t=20→0.0、t=39→0.095、t=40~54→0.100 | **机制正确**（公式 24 逐点吻合） |
| **KL 裁剪** | `[0, 10]`，`kl_reduction="mean"` | **KL 实测 mean 0.0234 / max 0.0264**，6 个 batch **命中上限 0 次** | **从未触发**（安全阀）。可写"未触发、VIB 未被静默关闭"，**不可以写"KL 裁剪起了作用"** |
| **梯度裁剪** | `L2 ≤ 5.0` | backward 后 clip 前总范数：β=0 时 **418.7 / 108.9**；β=0.1 时 **130.6 / 89.1** | **每一步都触发**，缩放比仅 **0.012~0.038** |

关键量（best.pt 的 VIB 后验状态）：

- `μ` 的 mean|μ| ≈ **0.17~0.20**，RMS ≈ 0.189
- `σ` 均值 ≈ **0.981**（范围 0.83~1.15）—— 几乎停在初始化点 (μ=0, σ=1)
- ⇒ 潜码 `z=μ+εσ` 里**噪声方差 σ²≈0.96 是信号方差 μ²≈0.036 的约 26 倍**，即约 96% 是噪声
- 但**推理走 `sample_vib=False` ⇒ z = μ（确定性）**，部署时无噪声（`trainer.validate` 与
  `src/deploy/inference.py` 都是这样），所以指标不受影响

**这组数说明什么**：β=0.1 下的信息瓶颈**非常弱**——KL 只有 0.023，
VIB 项的最后实测值 `raw={'vib': 0.0216}`（含分类交叉熵），其中正则部分
`β·KL = 0.1×0.0234 = 0.0023`，**约占该项的 11%**。所以：
**"VIB 抑制过拟合"目前只能作为机制陈述，没有任何数值证据**。
要拿到证据，只有两条路——`no_vib` 对照臂（重训）或 β 扫描。

#### (b) ★ 一处真正的设计缺陷：β 退火的"生效窗口"与 VIB 的"可训窗口"不重叠

由 `history.json` 逐轮 `beta` 与 `train_raw` 键名可直接读出：

| 阶段 | global epoch | β | `train_raw` 里有 `vib` 吗 | VIB 参数是否可训 |
|---|---|---|---|---|
| stage1 | 0–19 | **0.0** | ✅ 有（`use_tasks: ["cls"]`） | ✅ 可训 |
| **stage2** | **20–39** | **0 → 0.095（升温中）** | ❌ **没有**（`use_tasks: ["loc","edge"]`） | ❌ **被冻结**（`freeze: ["vib","cls_head"]`） |
| stage3 | 40–54 | **0.100（恒定）** | ✅ 有 | ✅ 可训 |

也就是说：**β 从 0 升到 0.1 的那 20 轮，恰好整个落在 VIB 既不参与损失、参数也被冻结的阶段。**
在这 20 轮里 β 取什么值对任何事情都没有影响。等 stage3 把 VIB 解冻时，β 已经是上限 0.1。

⇒ **"β 退火"在本次正式训练中并没有起到退火作用，实际表现为 stage1 → stage3 之间的
一次 0 → 0.1 阶跃。** 这一步是**在模块被解冻的瞬间以最大强度接管**，
恰恰是退火本来要避免的情形。

加剧这一点的是配置里的 `beta_epoch_offset`：

```yaml
# configs/default_crossval.yaml:223（default.yaml:177 同）
    - name: "stage3_joint_finetune"
      beta_epoch_offset: 20            # 承接 β 退火：t=20 起开始升 β
```

trainer 里是 `beta = beta_schedule(global_epoch + stage.beta_epoch_offset)`。
stage3 起始 `global_epoch = 40` ⇒ `t = 40 + 20 = 60 ≥ 40` ⇒ **直接饱和在 0.1**。
`+20` 的效果与注释想表达的"t=20 起开始升"**方向相反**；
若要 stage3 内部平滑升温，offset 应为 **−20**（把 stage3 起点映射到 t=20）。
换言之：**这行设置是个不起作用的设置**（+0 与 +20 结果完全相同）。

**修法（推荐 ②）**：

| 方案 | 做法 | 优缺点 |
|---|---|---|
| ① 保持三阶段编排，只改 offset | `beta_epoch_offset: -20`，让 stage3 内部走完 0→0.1 的升温 | 一行改动；但 stage1 仍是"β=0 训 VIB 20 轮" |
| ② **把 β 退火重新锚定到"VIB 激活的轮次"而非全局轮次**（推荐） | 在 trainer 里为"VIB 参与的 epoch"单独计数 `vib_epoch`，`beta = beta_schedule(vib_epoch)` | 语义正确、不依赖三阶段编排的巧合；改动约 5 行 + 一条自检断言 |
| ③ 放弃退火叙事 | 明确写成分段常数 β（stage1: 0；stage3: 0.1），删掉"退火"表述 | 最省事、最诚实；但少一个卖点 |

**必须在报告里补的自检**：训练日志应当**逐轮打印 `kl_raw` / `kl_clipped` / `grad_norm`**。
现在 `train_log.txt` 全文搜索 `kl`、`grad_norm`、`clip` 均为 **0 次命中**——
三个机制里只有 β 有日志证据。没有这三行日志，上面这些结论都只能靠今天新写的诊断脚本
在**事后**补出来，而且每次都要重新加载 362 MB 权重。

#### (c) 修复已落地并端到端验证（2026-09-29）

上面 (b) 的**修法 ② 已实施**，随附日志补丁与一条启动断言。三处改动：

| 改动 | 文件 | 内容 |
|---|---|---|
| β 重新锚定 | `src/engine/trainer.py` | 新增 `beta_anchor`（`global` / `vib`）；`vib` 锚只在 `use_tasks` 含 `cls` 的轮次上推进计步 |

**★ 陷阱：只改锚不够。** 旧值 `stage3.beta_epoch_offset: 20` 在 `global` 锚下是空操作；
但在新的 `vib` 锚下，它会把 stage3 的起始锚从 20 直接推到 **40（= `warm_e`）** ⇒
β 一上来就是 0.1，**退火被跳过，症状与原来完全一样**。两处必须一起改。

**启动断言**（`_check_beta_window()`，在训练开始前跑，不通过就不启动）：

| 情形 | 判据 | 处置 |
|---|---|---|
| 退火**未启用** | 最大锚值 < `warmup_start` | 只**警告**（demo / `--epochs-scale 0.05` 这类短跑天然如此，硬失败会把冒烟测试全打死） |
| 退火**被跳过** | 锚越过整个升温区间，却无任何一轮落进 `(warm_s, warm_e)` | **硬失败** |
| 退火**空转** | 升温区间 ∩ VIB 参与区间 = ∅（09-28 的原症） | **硬失败** |

**demo 冒烟实跑证据**（`scripts/train.py --demo --epochs-scale 0.05`，`exit=0`，13 min，
三阶段全跑完；日志 `outputs/diag/smoke_beta_log_patch.log`）：

② `kl_raw` / `kl_clip` / `grad_norm` 逐轮落盘，**stage2 为 `nan` 属预期**（`use_tasks` 不含 `cls`，

**★ 对 §2.2(a) 表中"梯度裁剪"判读的修正（自我纠正）**：上表"缩放比仅 0.012~0.038、
近乎空操作"是在**已收敛的 `best.pt`** 上量的。日志打通后首次测到**训练早期**
`grad_norm` 高达 **1.5e5 ~ 2.2e5**（stage1/stage2），与收敛后的 89~419 **差 3 个数量级**；
demo 的 stage3（已过两阶段预热）为 **45~52**。
⇒ **"近乎空操作"只在收敛后成立，训练早期裁剪是实打实在工作的。**
报这条必须限定适用范围；正式训练跑完才有全程曲线。

**★ 日志补丁里差点踩的静默事故**：诊断量**绝不能放进 `losses["raw"]`** ——
`raw` 会被逐项归一化（公式 30）再加权求和为 `total`（公式 31），
**多一个键 = 往目标函数多加一项损失**，且不报错。故另开只读的 `losses["diag"]`。

### 2.3 Mobile-UNetv2 定位头 + Canny 边缘监督

**实现**：`src/models/mobile_unetv2.py`（`MobileUNetV2` / `EdgeHead` / `canny_edge` /
`LocalizationBranch`）+ `src/losses/multi_task.py` 的 `edge_loss`，对应公式 (28)(29)。
参数量 **3.690 M**，占整机 4.08%。

- 解码器 3 个 `UpBlock`，用 `interpolate(size=skip.shape)` 对齐，规避奇数尺寸误差
- 上采样统一走 `_bilinear_upsample_fp32()`：autocast 下 bf16 的
  `upsample_bilinear2d` **反向**在 CUDA 上走未向量化 atomicAdd 慢路径，
  单次实测 2.9 s（fp32 仅 7 ms，差 400 倍）——**这个坑不修会让 stage2 慢 8 倍以上且不报错**
- 边缘 GT 由 `EdgeHead.canny_edge(mask_gt)` 在线提取（公式 29），不是预生成
- 三条证据表明它**确实在训练**：① 权重里 `localization` 参数 3.690 M 非空；
  ② `history.json` 每轮的 `train_raw` 都含 `edge`（stage2/3 共 35 轮）；
  ③ 末轮 `train_raw['edge'] = 0.0175`，不确定性加权给它的权重 `w_edge = 1.227`

**定位实际学到了什么**（`history.json` 的 `val_loc_miou_tampered_only`）：

| 阶段 | 起 | 止 | 说明 |
|---|---|---|---|
| stage1 | 0.0985 | 0.0985 | 定位头**冻结**，恒为初始值（合理） |
| **stage2** | **0.0290**（ep20） | **0.2770**（ep33） | **从"几乎不会"涨到 0.277**，是定位头真的在学的直接证据 |
| stage3 | 0.2753 | 0.2691 | 平台期，**在 0.27 附近来回，再没涨** |

⇒ **定位支路是"训起来了但没学够"（欠拟合），不是"没训起来"。**
0.2668 的测试值 vs 目标 0.56，差距来自容量/数据/监督强度，而不是流程错误。

  ForenSynths（20000 张，含 8 个**未见生成器**）把整体拉低。**这不是模型变差了，
  是任务变难了**，两个数不可混着说。
- **AUC 0.9051 与 ACC 0.7621 的巨大落差是本项目最值得讲的一条**：
  混淆矩阵 TN=6318 / FP=4432 —— **在全部 10750 张真实图上，有 41% 被判成伪造**。
  即模型的**排序能力尚可（AUC 0.905）但判决阈值严重偏向"判伪造"**。
  零推理成本的阈值扫描（`outputs/protocol_20260929/threshold_sweep.md`）显示：
  把阈值从 0.5 提到 0.99，严格跨生成器宏平均 ACC 可从 0.6696 提到 **0.6940**
  （半劈 holdout 无偏估计，+0.0244），**不需要重训**。
  ⇒ 论文里必须写清用的是哪个阈值；**0.5/0.99 两个数不能混报**。

### 3.3 跨生成器泛化（论文主表）

| 口径 | 生成器数 | 宏平均 ACC | 说明 |
|---|---|---|---|
| 标准协议 | 13（含 progan） | **0.6923** | progan 与训练同源、ACC 恒 1.0，**混在一行报等于自报虚高** |
| 严格跨生成器 | 9（排除 progan + 留出的 3 个） | **0.6696** | ← 论文报这个 |

**它说明什么**：模型对**未见生成器**的整图检测宏平均 ACC 只有 0.67，

所以 val 比 test 易约 0.09 —— 方向保守，不会虚报。

### 3.4 三条"没有数据"，答辩前必须知道

1. **逐模块消融 = 零数据。** `no_cross_attention` / `no_vib` / `no_edge` / `no_phase` /
   `no_learnable_mask` / `no_grad_stop` 六条臂**一次都没训过**。
   现有唯一的对照是「骨干权重」消融（`random` vs `pretrained`）。
2. **训练集只用了约 5.6%。** 配置 `max_samples: 40000`（`configs/default_crossval.yaml:45`）
   封顶，正式训练实际是 46000 张 = ForenSynths(train) 40000 + CASIAv2(train) 6000
   （`gpu_train_log.txt`）。而下载到的训练集是 **74.9 GB / 约 72 万张**
   ⇒ **本次训练用的是其中的约 5.6%**。汇报时说"用了 74.9 GB 训练集"是不准确的。
3. **COVERAGE 三个 split 全部缺失**，训练日志有 ⚠ 提示但被跳过：
   `COVERAGE(train)` / `COVERAGE(val)` / `COVERAGE(test)` 各"配置了 1 个数据集但一个样本都没有"。
   ⇒ **跨数据集定位泛化无数据**；而且评测 A 与评测 B 的 `loc` 段**逐位相同**，
   说明定位只在 CASIAv2 上测了**一次**，不构成独立证据。

### 3.5 补充核查：早停为什么停在 global 54（2026-09-29 追）

**机制**：`configs/default.yaml` 早停配置 = `monitor: val_cls_auc`、`early_stop_patience: 8`，
判据是 `metric > best_metric`（**严格大于，无 `min_delta`**），且 **patience 与 best 在每个阶段开始时重置**
（`trainer.py:260-263`）。三阶段为 stage1 0–19 / stage2 20–39 / stage3 40–69，
stage3 计划 30 轮。

**实测**（`history.json`）：stage3 内 `val_cls_auc` 的最高值出现在 **epoch 46 = 0.99908**，
其后 **epoch 47–54 连续 8 轮均未超过它** → 触发 patience=8 → 停在 54。
算术上 **54 = 46 + 8**，完全吻合。

**但"到顶了"是假象**——根因是**监控指标已经饱和、失去区分度**：

| 阶段 | `val_cls_auc` 表现 | 判读 |
|---|---|---|
| stage1 | ep3 起 0.9993，ep5 到 0.99946 后 15 轮在 0.9992~0.99946 抖动，**极差 ≈ 0.001** | 早已饱和 |
| stage3 | 全程 0.99646~0.99908，**极差 0.00262、标准差 0.00070** | 全程在噪声带内 |

val 用的是 `progan_val.zip`（ForenSynths/val 8000 张，**与训练同源 ProGAN**）+ CASIAv2 val，共 9261 张。
在一个已被压到天花板的指标上执行"连续 8 轮不破纪录"，**几乎必然触发**：
epoch 46 之后那 8 个值只比历史最优低 0.00065~0.00101，是**噪声**而非"性能见顶"。

**三个直接后果**：

1. **stage3 的 30 轮里 15 轮被丢弃**（只用了 40–54），`lr 1e-5→1e-7` 的余弦退火只走了一半。
2. **`best.pt` 是 epoch 46 的权重**，而 0.998~0.999 区间十几个 checkpoint 的 `val_cls_auc`
   差异全在噪声内 ⇒ **"按 val 挑最优权重"这一步实际是随机的**。
   —— 这正是 P0-⑥「换 val_cross」要修的问题（新 val_cross AUC 0.9327，恢复区分度）。
3. stage3 是**同时训分类 + 定位 + 边缘**的阶段，而停止决策**只看已饱和的 `val_cls_auc`**，
   完全没有反映多任务目标。（注：stage3 的定位 mIoU 本身也是平台 0.2753→0.2691，
   所以**不能**据此断言"定位被早停砍掉了改进空间"——只能说这个停止判据与多任务目标无关。）

**修法**：① 换有区分度的 val（`configs/default_crossval.yaml`，已做）；
② stage3 的 `monitor` 改成多任务组合量或 `val_loc_miou`；
③ 给 stage3 固定轮数 / 加大 patience。
（**注意**：加 `min_delta` **不是**解药——它让"提升"更难成立，只会**更早**早停。）
