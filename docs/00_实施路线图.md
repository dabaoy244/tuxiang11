## 〇、先看清这个项目的真实工作量

申报书写的起止时间是 **2026.06 — 2027.06，共 12 个月**，团队 3 人。
按实际经验，这个项目的工作量大致是：

| 类别 | 工作量占比 | 说明 |
|---|---|---|
| 环境与数据 | 20% | 数据下载/清洗/划分最耗时间，尤其是跨生成模型数据集 |
| 模型实现与调试 | 25% | 代码本仓库已给，主要是跑通 + 对齐公式 |
| 训练与调参 | 30% | **最耗时间**。70 轮三阶段训练，一次完整实验在单卡 3090 上约 1~2 天 |
| 评测与实验 | 15% | 评测本身快，但消融要**重训 7 次**，这是隐藏的大坑 |
| 系统开发与论文 | 10% | PyQt5 工具（本仓库已给）+ 论文撰写 |

**最容易低估的两件事：**
1. **消融实验要重训 N 次。** 7 个消融项 × 每次 1~2 天 = 至少两周的连续算力占用。
   必须提前排算力档期，或者先把轮数降到 40 轮做消融、最后用完整轮数跑主实验。
2. **跨生成模型泛化性（ForenSynths 准确率 ≥91%）不是调参能调出来的。**
   这条指标靠的是「训练集生成模型种类足够多 + VIB 去冗余」。如果训练集只用了
   一种生成器，指标一定上不去，此时要做的是**扩数据集**而不是改超参。

## 二、阶段一：环境与数据（2026.06–07）

### 步骤 1.1 搭环境

```bash

conda create -n vibnet python=3.10 -y && conda activate vibnet

# PyTorch（按显卡 CUDA 版本选，下面以 CUDA 12.1 为例）
pip install torch torchvision --index-url https://download.pytorch.org/whl/cu121
pip install -r requirements.txt
```

**验证环境是否就绪：**
```bash
python scripts/smoke_test.py
# 期望：测试结果：29/29 通过
```

> 这一步的脚本会把申报书里 **每一条公式的张量维度**都打出来核对一遍。
> 如果某条公式的维度和申报书对不上，脚本会直接报 FAIL —— 这是最早、最便宜的排错时机。

⚠ **CLIP 权重问题**：`transformers` 默认不会联网下载。要么：
- 设 `export VIB_NET_ALLOW_DOWNLOAD=1` 让脚本联网拉 `openai/clip-vit-base-patch16`；
- 要么事先下好权重放到 `pretrained/clip-vit-base-patch16/`（推荐，实验室机器常常不通外网）；
- 临时验证流程可以用 `backbone: tiny_vit` 走兜底骨干（**指标无意义，仅用于跑通**）。

### 步骤 1.2 准备数据集

```bash
python scripts/prepare_datasets.py --root data/Datasets --check
```

脚本会打印三套数据集的获取渠道和当前落盘情况。拿到数据后：

```bash
python scripts/prepare_datasets.py --root data/Datasets --organize --mode link
python scripts/prepare_datasets.py --root data/Datasets --manifest
```

**`--mode link` 用硬链接组织数据，不额外占磁盘**（10 万张图像复制一遍会多占几十 GB）。

三套数据集的作用必须分清，**不要混用**：

| 数据集 | 用途 | 有无像素掩码 | 评测维度 |
|---|---|---|---|
| ForenSynths | 训练/评测**整图真伪** | ❌ 无 | ACC / P / R / F1 / mAP |
| CASIA v2 | 训练/评测**篡改定位** | ✅ 有 | mIoU / PixelAcc / Dice |
| COVERAGE | 评测**细粒度定位** | ✅ 有 | mIoU（更严格的逐图均值） |

### 步骤 1.3 数据划分要写进论文

`--manifest` 会把每条样本的来源、标签、掩码路径、split 写进 `data/Datasets/manifest.json`。
**论文里"数据划分可复现"就靠它**，答辩时被问到"你怎么划分的"可以直接给出文件。

**验收标准：** `manifest.json` 里三个数据集的 train/val/test 都有样本，
且各 split 的正负样本比例接近（脚本已做分层抽样）。

## 三、阶段二：复现基线（2026.08–09）

**为什么必须做这一步：** 没有基线，你的"提升 8%"没有任何意义；
而且复现过程中你会真正理解频域方法为什么在 JPEG 压缩下崩掉 —— 这是写论文引言最有力的素材。

### 步骤 2.1 选定 2~3 个基线

申报书 3.3 已经点名了三个，按可复现性排序：

| 基线 | 类型 | 复现难度 | 代码可得性 |
|---|---|---|---|
| **CLIP-based Detector**（Ojha et al., CVPR 2023） | 空域（CLIP 特征） | ★★ | 官方开源，最好复现 |
| **BiHPF**（Jeong et al., WACV 2022） | 频域（双边高通滤波） | ★★ | 官方开源 |
| **DIRE**（Wang et al., ICCV 2023） | 扩散重构误差 | ★★★★ | 需要预训练扩散模型，显存吃紧，**建议只做定性对比** |

**建议组合：** CLIP-based Detector + BiHPF 做定量对比，DIRE 用作者给出的公开结果做定性引用。

### 步骤 2.2 统一评测协议

这一步极其重要，**做错了前面所有实验都要重来**：

1. 用**同一套测试集**、**同一套划分**（都用步骤 1.3 的 manifest）；
2. 统一输入分辨率（本仓库统一 224×224，中心裁剪保长宽比）；
3. 统一指标实现（直接用 `src/engine/metrics.py`，保证自己的模型和基线用同一套代码算指标）；
4. 记录**每一类后处理**下的指标，不只看原图 —— 这是本项目的卖点之一。

**验收标准：** 基线指标与原作者论文报告值的差距 **<3%**。
如果差很多，先怀疑：① 测试集划分不一致；② 图像预处理不一致（JPEG 二次压缩！）；
③ 指标口径不一致（很多论文报的是 AUC 而不是 ACC）。

## 四、阶段三：空频双分支 + 分层 VIB（2026.10–11）

代码已在 `src/models/` 里写好，这一阶段的核心工作是**验证单模块有效性**，
而不是重写代码。

### 步骤 3.1 先把中间特征"看"出来

先跑这个，肉眼确认模块真的在工作：

```python
import torch
from src.models.vibnet import build_model, load_config

cfg = load_config("configs/default.yaml")
model = build_model(cfg).eval()
x = torch.randn(1, 3, 224, 224)
out = model(x, sample_vib=False, return_intermediate=True, beta=0.0)

# 频域掩码长什么样？应该是"中间亮、边缘暗"或"若干同心环带"
mask = out["freq_mask"]
# 可视化建议：mask[0,0].numpy() 用 matplotlib imshow(cmap='viridis')
```

**要重点观察三件事：**
1. **可学习频域掩码**是否学到了**非中频**的结构？如果掩码几乎全 1 或全 0，
   说明它退化了（解决：给掩码加 L1 稀疏约束，或降低掩码网络学习率）。
   这是论文里最有说服力的一张图，一定要画。
2. **相位支路 vs 幅值支路**的特征激活强度对比。申报书说"相位贡献是幅值的 1.7 倍"，
   这个数字**必须你自己实验测出来**（消融 no_phase vs full 的差值），
   **不要直接引用**——否则答辩时被问"1.7 倍怎么来的"会很尴尬。
3. **VIB 的 KL 值随训练的变化**。健康曲线：KL 缓慢上升然后趋于平稳（比如稳定在 0.3~2）。
   危险信号：KL 一直在涨（瓶颈失效）或直接掉到 0（后验坍缩 posterior collapse）。

### 步骤 3.2 单模块消融

```bash
python -m src.evaluation.ablation --demo --mode eval    # 先自检流程
python -m src.evaluation.ablation --mode train          # 正式：每个消融项独立训练
```

四个模块（`no_learnable_mask` / `no_phase` / `no_cross_attention` / `no_vib`）
都要有**可观测的指标差异**。如果某项差异 <0.5%，说明该模块没起作用，需要：
- 检查该模块是否真的被"关掉"了（本仓库的消融是改配置，会自动重建模型结构）；
- 检查训练轮数是否太少（模块没来得及体现价值，需要 ≥40 轮）；
- 检查学习率是否让该模块没学动。

**验收标准：** 四个模块消融表的 ΔACC 或 ΔmIoU 至少有两项 >1%，
且方向符合预期（去掉模块后指标下降）。

## 五、阶段四：双支路 + 联合训练（2026.12–2027.01）

### 步骤 4.1 三阶段训练

```bash
python scripts/train.py --config configs/default.yaml
```

配置在 `configs/default.yaml` 的 `train.stages` 里，对应申报书 1.4(3)：

| 阶段 | 轮数 | 冻结 | 训练 | lr | 目的 |
|---|---|---|---|---|---|
| ① 分类预训练 | 0–20 | localization | spatial+freq+fusion+vib+cls_head | 1e-4→1e-6 | 学基础真伪判别 |
| ② 定位预训练 | 20–40 | vib+cls_head | spatial+freq+fusion+localization | 5e-5→5e-7 | 学细粒度定位 |
| ③ 联合微调 | 40–70 | 无 | 全部 | 1e-5→1e-7 | 协同优化 |

**监控什么：**
- 每个 epoch 看 `outputs/run_default/train_log.txt` 里的 `raw=` 字典。
  四个损失项的量级应该在同一量级（因为已经 Z-score 归一化了）；
  如果不一致，说明归一化窗口太短（把 `zscore_window` 从 100 提到 200）。
- 看 `weights=` 里四个 `sigma_*` 的演化。它们会**自动分化**（有的升有的降），
  这就是"自动权重分配"的证据，**论文里要画这张图**。

### 步骤 4.2 三个最容易失败的点

| 症状 | 原因 | 解决 |
|---|---|---|
| 定位支路输出全黑 | 混合批次里 ForenSynths 样本的补零掩码污染了梯度 | 已用 `mask_valid` 过滤；**自己改代码时切勿丢掉这个机制** |
| 分类 ACC 卡在 50% | CLIP 前 6 层若没冻结，小 batch 会把预训练权重带崩 | 检查 `freeze_first_n_layers: 6`；batch 提到 ≥16。⚠️ **2026-09-26 之前调这个字段不会有任何变化**（被 `apply_stage()` 静默覆盖，见 docs/08 D41）；本版起生效，判据是日志出现 `[阶段重放] 冻结前 6/12 层` |
| 定位 mIoU 上不去但 BCE 很低 | 篡改区域面积小，被背景像素淹没 | 提高 Dice 权重（`uncertainty_weighting: false` + `weights.dice: 3.0` 先验证）；或对 BCE 用正样本加权 |

**验收标准（申报书 6.3）：**

| 指标 | 目标 | 本仓库对应命令 |
|---|---|---|
| ForenSynths 检测 ACC | ≥91% | `python -m src.evaluation.evaluate --split test` |

**篡改定位（三次口径并列，A/B 两次评测数字完全相同）：**

| 口径 | 值 | 用途 |

| ① 池化 `miou` | 0.4570 | 仅看训练趋势 |

Pixel Acc = 0.9748，Dice = F1 = 0.6273，定位样本数 1263。

**推理性能：** 参数量 90.53 M，FP32 体积 362.1 MB；
单张延迟 0.45 ms / 2220 张·秒⁻¹（评测 A）、1.15 ms / 867 张·秒⁻¹（评测 B）—— **均为 `device=cuda`**。

**⚠ 四个必须知道的坑（本次实测暴露）：**

1. **"CPU 推理达标"是口径错误，不能引用。** `eval_*.json` 的 `targets` 里把
   `CPU 推理 >= 8 张/秒` 判为 `true`，但同一份 JSON 的 `"device": "cuda"` ——
   它是拿 4090 上的 2220 张/秒去比 CPU 目标。真实 CPU 吞吐见 `docs/09`：
   b16 无论 FP32 还是 INT8 都只有 **2.86 张/秒**（本机 CPU 无 VNNI），
   要换 `configs/lite.yaml`（s16 骨干）才到 9.46~11.22 张/秒。**这条需重测后才能写进验收。**
2. **评测 A 与评测 B 的定位数字完全一样**，因为评测 A 的定位子集就是同一批 1263 张
   CASIAv2 test。所以"两次评测"在**定位**上不含独立信息，等于只测了一次。
3. **ForenSynths 单独的 ACC 根本没测**，91% 这条目前**无数据**，不能声称达标。
4. **COVERAGE 数据集缺失**（`COVERAGE/train` 目录不存在），两次评测均跳过，
   跨数据集定位泛化（COVERAGE）无数据。

**如果 ACC 达不到 91%：** 优先做的事依次是
① 扩训练集生成模型种类（这是核心）；② 加长训练轮数到 100；③ 调 β 上限（0.1 → 0.3）；
④ 最后才调学习率。

**如果 mIoU 达不到 56%：** 优先做的事依次是
① 提高定位头分辨率（把 `refine_channels` 提到 64）；② 加边缘损失权重；
③ 检查切图/缩放是否把细粒度线索压没了（考虑 256 或 320 输入）。

## 六、阶段五：部署与桌面工具（2027.02–03）

```bash
# 1) 导出 ONNX（opset 17，常量折叠，参数内嵌 —— 申报书 3.1 要求）
python -m src.deploy.export_onnx --ckpt checkpoints/vibnet_best.pt \
       --out deploy/vibnet.onnx --simplify

# 2) 转 OpenVINO IR 并测速
python -m src.deploy.optimize_openvino --onnx deploy/vibnet_simplified.onnx --out deploy/vibnet_ir --bench

# 3) INT8 量化（体积优先时用；★ 注意实测会变慢，见下方警告）
python -m src.deploy.quantize_int8 --onnx deploy/vibnet_simplified.onnx --out deploy/vibnet_int8.onnx
python -m src.deploy.optimize_openvino --onnx deploy/vibnet_simplified.onnx --int8

# 3b) 指标验收：体积 + CPU 吞吐（不要用 PyTorch eager 报吞吐）
python scripts/benchmark_cpu.py --reps 5 --runs 20
python scripts/measure_backbone_budget.py

# 4) 启动桌面工具
python app/main.py
```

⚠ **这一步有硬仗**：CLIP-ViT-B/16 的 FP32 体积实测 **362.1MB**（非估算），**远超 120MB 指标**。
而且实测发现三条出路里只有前两条真的可行（详见 **`docs/09_指标可达性与骨干选型.md`**）：

1. **换轻量档骨干 s16**（★ 首选）：`configs/lite.yaml` → **98.7MB + 9.46~11.22 张/秒**，
   **两项硬指标同时达标，且不需要量化**；
2. **保留 b16 + INT8 量化**：体积 92.9MB 达标，但 CPU 只有 2.86 张/秒，
   且实测**动态 INT8 比 FP32 慢 3.3 倍**（batch=1 时反量化开销 > INT8 矩阵乘收益，
   本机 CPU 无 VNNI）—— 量化省体积，**不省时间**；
3. 知识蒸馏到小骨干（成本最高，建议作为后续工作而非本期目标）。

> 原文档里"INT8 量化后 CPU 还更快"的判断**已被实测推翻**，请以 `docs/09` 为准。
> 另外注意：验收吞吐必须走 ONNX/OpenVINO 路径，**不要用 PyTorch eager 报指标**
