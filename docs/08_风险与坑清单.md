## A. 会在项目后期才暴露、但后果最严重的三个坑

### A1. FFT 无法导出 ONNX（★ 最隐蔽）

**症状**：训练全部完成后，`torch.onnx.export` 报
`UnsupportedOperatorError: Exporting the operator 'aten::fft_fft2' to ONNX opset version 17 is not supported`。

**为什么严重**：此时改模型结构意味着前面所有训练白跑。

**提前规避**：本仓库已内置 matmul-DFT（`src/models/dft.py`），
`export_onnx.py` 会自动切换。**自己改频域分支时，务必避免引入 `torch.fft` 系列算子。**

**验证时机**：阶段三的第一次训练出 checkpoint 后立刻跑一次导出，
不要等到阶段五。

```bash
python -m src.deploy.export_onnx --ckpt checkpoints/vibnet_best.pt --out /tmp/t.onnx
```

### A2. 模型体积指标与骨干选择冲突（★ 已实测确认，申报书内部矛盾）

**症状**：结题时发现模型的 FP32 体积 **362.1MB**，远超申报书的 ≤120MB。

**已实测的结论**（不是估算，全部数据见 **`docs/09_指标可达性与骨干选型.md`**）：

| 方案 | 体积 | CPU 吞吐 | 结论 |
|---|---|---|---|
| b16 骨干 + FP32 | 362.1 MB | 1.67 张/秒 | 两项都不达标 |
| b16 骨干 + INT8 | 92.9 MB | 2.86 张/秒 | 只有体积达标 |
| **s16 骨干 + FP32 + ONNX 简化** | **98.7 MB** | **9.46~11.22 张/秒** | **两项都达标** |

**提前规避**：直接用 `configs/lite.yaml`（s16 档）作为验收配置，
不需要量化就同时打中两项指标。**6 月就把这条链路跑通一次**：

```bash
python -m src.deploy.export_onnx --ckpt "" --config configs/lite.yaml --out deploy/lite.onnx
python scripts/benchmark_cpu.py --reps 5 --runs 20
```

### A2b. 三个"看起来是加速、实际是坑"的认知错误（★ 实测推翻）

**坑 1：以为 INT8 量化会更快。**
实测 lite 档 FP32 延迟 89.2ms → INT8 延迟 **298.6ms**，**慢了 3.3 倍**。
原因：batch=1 时 `DynamicQuantizeLinear` 的反量化开销 > INT8 矩阵乘省下的时间，
且本机 CPU 无 VNNI 指令。
→ **量化省体积，不省时间。** 体积指标走 INT8，速度指标走 FP32。

**坑 2：用 PyTorch eager 报吞吐指标。**
同一模型 PyTorch 392ms vs ONNX Runtime 89ms，**差 4 倍**。
申报书 3.1 的指标口径是"经模型封装与 CPU 加速优化后"，
**验收必须走 ONNX/OpenVINO 路径**，否则会白白判自己不达标。

**坑 3：只测一次就写进报告。**
同一模型连续三轮 PyTorch 延迟 518 / 358 / 411 ms（**±30%**）。
→ 用 `scripts/benchmark_cpu.py`（取多轮中位数），并在报告里写明
CPU 核心数、onnxruntime 版本 —— 否则被追问"什么机器跑的"就答不上来。

### A2c. 改了骨干档位，旧 checkpoint 全部失配

**症状**：`RuntimeError: size mismatch for spatial.backbone.clip.blocks.0.mlp.0.weight,
copying a param with shape torch.Size([1536, 768]), the shape in current model is
torch.Size([3072, 768])` —— 只看报错完全猜不到是"骨干档位变了"。

**已修复**：`src/models/spatial_branch.py` 提供
`infer_backbone_variant()` / `align_cfg_to_checkpoint()`，
从权重形状（MLP 隐层宽度 + 层数）反推档位并自动对齐配置，
在 `evaluate.py` / `robustness.py` / `inference.py` / `export_onnx.py` / `trainer.load()` 五处都已接入。

**自己改档位或换骨干时请记得**：checkpoint 与 YAML 的 `backbone_variant` 必须一致，
否则 `trainer.load()` 会抛出带清晰指引的报错（见实现）。

| # | 坑 | 症状 | 规避 |

### C19：AMP 的两个坑 —— "能跑但会把人坑死" 与 "看起来在防溢出"（2026-09-22，已修）

**背景**：`configs/default.yaml` 里 `amp: false`，因为本机没有可用的 CUDA。
也就是说 **AMP 这条路径在本机从来没被跑过** —— 它会在上云第一次启用，
而云上按小时计费。这种"唯一一次测试发生在花钱的时候"的代码，必须先在本机
把**决策逻辑**钉住（做法见本轮新增的 `smoke_test.py::test_amp_policy()`）。

**坑 1：CPU 上的 bf16 autocast 不是"慢一点"，是慢 30 倍以上。**
实测（同一个 demo 任务，每 epoch 3 个 batch）：
| 配置 | 结果 |
|---|---|
| fp32（默认） | 单 epoch 约 25 s |
| `--amp`（CPU bf16 autocast） | **15 分钟连 1 个 epoch 都没跑完**（被 timeout 杀掉） |

原因：普通 x86 没有 AMX/VNNI，bf16 只能走低效的转换/仿真路径。
torch 支持 CPU 上的 bf16 autocast 是事实，但**"支持"不等于"值得用"**。
→ 处置：`resolve_amp()` 里 **CPU 上一律强制关闭**，并打印一行说明；
配置误开 `amp` 时给出明确日志，而不是安静地慢 30 倍。

**坑 2：bf16 不需要 GradScaler，开着它只是"看起来在防溢出"。**
原实现是 `self.scaler = GradScaler(enabled=self.amp) if self.amp else None`，
**不区分 dtype**。但 bf16 的指数位与 fp32 相同（都是 8 位），动态范围不会溢出，
loss scaling 纯属多余；开着只会多一次 scale/unscale、触发 UserWarning。
更糟的是它给出**假安全感** —— 让人以为溢出已被处理，从而不去查真正的数值问题。
→ 处置：`scaler` 只在 **fp16**（`amp_dtype: float16`）时创建；bf16 恒为 `None`。

**统一入口**：`src/engine/trainer.py::resolve_amp(tcfg, device_type)`
→ 返回 `(enabled, amp_dtype, need_grad_scaler)`，真值表 6 条断言进自检。

> **教训（可推广）**：凡是"本机跑不到、只有花钱时才第一次跑"的配置分支
> （AMP / 多卡 / 分布式 / 云端专属路径），都要把**决策逻辑**抽成纯函数，
> 在本地自检里钉死真值表 —— 纯函数不需要那块硬件也能测。
> 与 D33 是同一类错误的两个面：**"看起来验证过"和"真的验证过"是两回事。**

| D11 | **HuggingFace 间歇性整体不可达，导致 70GB 下载全军覆没** | 见下方 D11 说明 |
| D12 | **预训练权重缺失时不报错，只是"训不动"** | 骨干随机初始化照样能跑完训练，只是 acc 恒 0.5。见 D12 说明 |

### D11：别把"一次下载失败"当成"这个源没有"

2026-09-18 实测：同一批 `progan_train.7z.001~007`（70 GB），

- 早上 `huggingface.co` 能跑 **8~11 MB/s**；
- 中午开始连续 **5 次探测全部超时**（`WinError 10060`），DNS 能解析但 TCP 不通；
- `hf-mirror.com` **可达但只有 0.28 MB/s**（70 GB 要 70 小时，等于不可用）；
- 下午再试又恢复到 **10 MB/s**。

**所以这是"间歇性阻断"，不是"源不可用"。** 原 `fetch_datasets.py` 只重试 4 次、
退避上限 20 秒，一次十几分钟的阻断就足以让 7 个分卷全部失败，而且它失败后
**继续去下下一个**，最后只留一行 `[FAIL]`，很容易被忽略。

已改为：
* 多镜像自动轮换（`hf` → `hf-mirror`），每次失败换下一个；
* 指数退避 15s → 300s，给网络恢复留时间；
* 默认重试 12 次（覆盖约 40 分钟的中断窗口）；
* 每次失败都重读本地大小断点续传，**已下部分绝不重下**。

**可复用的判断**：长下载失败时，先用一条极小的 `Range: bytes=0-1023` 请求探活，
再决定是"换源"还是"等一会儿"。区分"源不可用"和"暂时连不上"，
比反复重试整个大文件高效得多。

### D12：骨干权重缺失时，代码只会"安静地训不动"

`configs/lite*.yaml` 走的是 `backbone: tiny_vit`（`TinyViTFallback`，离线可构造），
它在 `pretrained/` 目录不存在时**不会报错**，只是随机初始化。后果：

```
epoch 1/5  val: cls_acc=0.5000  cls_auc=0.5125  tp=0 fn=800 fp=0 tn=800
epoch 2/5  val: cls_acc=0.5000  cls_auc=0.4928
```

`tp=0, fn=800` 说明模型把**全部样本都判成"真实"**，准确率恰好等于真实图占比。
这不是代码 bug，是**没有先验知识**的必然结果。

两个补救：
1. **`backbone_weights` 配置项**（本轮新增）：指向本地转换好的预训练权重，
   加载用 `strict=True` —— 键不匹配就**直接抛错**，而不是 `strict=False` 那样
   静默跳过一半参数。
2. **`scripts/fetch_pretrained_backbone.py`**：从 `download.pytorch.org`
   （可达性远好于 HuggingFace）取 ImageNet-1K 预训练的 ViT-B/16，
   转换成本仓库骨干命名，并做真实性校验（列出 missing/unexpected + 前向结构敏感度）。

**排查口诀**：如果分类指标"稳稳地"停在 0.5 附近，先去看
`val` 行里的 `tp/fn/fp/tn` —— 如果四个数里有一个是 0，说明模型根本没在做区分，
先怀疑骨干没加载到预训练权重，而不是先去调学习率。


### D9：那一行 `crashpad ... CreateFile: 系统找不到指定的文件。(0x2)`

现象：

```
[0918/111729.690:ERROR:third_party\crashpad\crashpad\util\win\registration_protocol_win.cc:108]
CreateFile: 系统找不到指定的文件。 (0x2)
```

**这不是我们的脚本报错，是 Git Bash / Electron 包装层的 crashpad 在每一次命令调用时都会往 stderr 打的一行噪音。**
判别方法很简单：随便跑一条 `ls`，它照样会打印这一行，而且退出码是 0（命令本身成功了）。

真正要判断"后台任务还在不在跑"，不要看这行噪音，用三重证据：

```bash
python scripts/check_status.py          # 进程 + 日志时间 + 进度
python scripts/check_status.py --watch  # 每 30 秒刷新
```

它会同时给出：① 进程表里还有没有这个脚本（最硬）；② 日志最后写入距今多久；
③ 日志里的进度数字（下载百分比 / 训练 iter）有没有推进。

**只有"日志长时间不更新"才值得警惕**。注意日志本来就是间隔写入的
（训练 `log_every: 20`，CPU 上约 76 秒一行），短暂"没动"通常只是还没到下一个打印点。

## F. 三条"如果只剩一周"的应急方案

**如果离中期检查只剩一周：**
1. 跑 `python scripts/smoke_test.py --full`，把 35 项自检结果截图当成果；
2. 用 `--demo` 跑一个完整的三阶段训练 + 评测，出一张训练曲线；
3. 启动桌面工具，录一段 1 分钟的演示视频。

**如果离结题只剩两周：**
1. 用真实数据跑 40 轮（不要 70 轮），拿到主指标；
2. 只做 3 个最重要的消融项（`no_vib` / `no_cross_attention` / `no_phase`）；
3. 鲁棒性测试只做 JPEG + 缩放 + 噪声三组；
4. 桌面工具直接演示，不做打包；
5. 论文投一个周期短的期刊/会议。

**如果发现模型完全训不起来：**
1. 先用 `backbone: tiny_vit` + `--demo` 确认**代码链路通**（如果这个都训不起来，是代码问题）；
2. 换回真实数据，把学习率降 10 倍再跑 5 轮看 loss 有没有下降趋势；
3. 检查标签是否反了（打印一个 batch 的图和标签肉眼确认）；
4. 检查 `mask_valid`、CLIP 冻结、BN 模式这三处。
