## 二、★ 两条必须先纠正的顺序问题

### 纠正 1：验证集重构必须**提前到 P1 之前**（原 P2 第⑥项）

`best.pt` 是「按最后阶段的 `val_cls_auc` 选最优」选出来的，而 `val_cls_auc` 在 epoch 13 就 0.9995 了。

> 带着这个饱和验证集去跑 P1 重训 → **新训出来的 `best.pt` 还是靠同一个坏依据挑** → 等于白烧一次卡。

而修它几乎不花卡时：只需改数据划分（把「跨生成器」成分挪进 val），再用**现有权重在本地 CPU** 上验证「新验证集是否恢复区分度」。
**这件事必须排在 P1 之前，不是排在 P2。**

### 纠正 2：P1 里有两件事其实零 GPU 成本，应并入 P0

- **ForenSynths 补测**：评测是纯推理。`evaluate.py` 已支持 `--dataset`（已确认 argparse 有该参数）。
  本机 CPU 也能跑（20000 张 × 2.86 张/秒 ≈ 2 小时），云端**无卡模式**（¥0.1/时）也行。**不需要 GPU、不需要重训。**
- **CPU 吞吐重测**：本来就是本机跑。

### 2.1 所以正确的划分是按「烧不烧卡」，不是按优先级名号

| 段 | 内容 | 卡时 | 费用 |
|---|---|---|---|
| **P0（无卡）** | ① 定位归因诊断 ② CPU 吞吐重测 ④ ForenSynths 补测 ⑥ 验证集重构 | **0** | ¥0 |

## 三、P0 —— 零成本，一个晚上做完（本机 CPU）

**前置**：本机托管 venv 有 torch（CPU 版）；权重在 `outputs/upload/results_20260928/_pack/vibnet_best.pt`。

### P0-① 定位归因诊断 ★ 最高优先级（先诊断，再烧卡）

**做什么**：写「按 GT 篡改面积分桶的 mIoU」，在现有权重上只跑 CASIAv2 test 的 1263 张（其中 513 张有篡改）。

**判据**：
- 小面积桶 IoU ≈ 0、大面积桶正常 → **小目标问题** → P1 优先提分辨率
- 各面积桶都不高 → **定位头能力不足** → P1 优先加边缘监督 / 换解码器

**耗时**：本机 CPU 约 15~30 分钟。**产出**：`outputs/diag_area_buckets.md`

**为什么必须先做**：不做就是猜。P1 一次训练 ≈ 9 卡时 ≈ ¥17 + 一晚时间；猜错两次就是白转 2 天。

### P0-② CPU 吞吐按正规路径重测

```bash
python -m src.deploy.export_onnx --ckpt "" --config configs/lite.yaml --out deploy/lite.onnx
python scripts/benchmark_cpu.py --reps 5 --runs 20
python scripts/measure_backbone_budget.py
```

**产出**：`outputs/cpu_benchmark.json` → 把 `docs/00` §4.3 里那条「⚠ 待重测」换成实测值。

### P0-④ ForenSynths 单数据集补测（把「无数据」变成「有数据」）

```bash
python -m src.evaluation.evaluate --ckpt checkpoints/vibnet_best.pt --split test --dataset ForenSynths
```

无论 91% 达标与否**都必须有数字** —— 中期检查一定会被问这一条。

### P0-⑥ 验证集重构（前置于 P1）★

**现状问题**：`val = ForenSynths(val) 8000 + CASIAv2(val) 1261`，与 `train` 同分布 → AUC 0.998 饱和，失去区分度。
**目标**：让 val 含「跨生成器」成分，能反映测试时真正面对的分布。

**三种做法（按代价升序，任选其一）**：

1. **最小改动**：从 `ForenSynths/test` 的 13 个生成器里**按生成器分层抽一部分**进 val（如每类 200 张），且与 train 的生成器不重叠；
2. 保留原 val，**另建 `val_cross`**，模型选择以它为准（改动最小、历史可比性最好）；
3. 重做 manifest 划分（最彻底，但历史结果不可比）。

**验收判据**：用现有 `vibnet_best.pt` 在新 val 上跑一次，**AUC 应显著低于 0.998（落在 0.90~0.95）**。
若仍是 0.998 → 说明划分没改对，别往下走。

**产出**：新的 `manifest.json` + `docs/05` 记录该口径变更。

## 四、P1 —— 需要烧卡（一次开机，约 13~22 卡时）

**铁律：一次只改一项。** 每次都走同一条流水线，避免手工漏测。

### P1-a 定位攻坚第一枪

按 P0-① 的归因结论二选一：

| 归因指向 | 改动 | 代价 |
|---|---|---|
| 小目标被压掉 | 输入分辨率 224 → 320（`configs/default.yaml` 的 `data.input_size`） | 单轮 ≈ 2.2×（470s → ~1000s），70 轮 ≈ 10 h |
| 定位头容量不足 | `refine_channels` 32 → 64 | 显存涨、耗时涨约 20% |

**建议同时做两件顺手的事**：
1. 把 `evaluate --dataset ForenSynths` 加进 `scripts/run_all_pipeline.sh`，以后不再单独补测；
2. 把验证集换成 P0-⑥ 的新划分（**这是纠正 1 的落地**）。

### P1-b 第二枪（视 P1-a 结果决定跑不跑）

若 P1-a 提升明显（mIoU 到 0.35+），再叠另一项；否则先做归因再决定。

### P1-c lite 骨干训练（与 a/b **分开**跑）

**目的**：一次性把**体积**和 **CPU 吞吐**两项硬指标坐实（98.7 MB / 9.46~11.22 张/秒均已实测）。

**前提**：lite 档的 ACC / 定位指标可接受。
若 lite 指标掉太多 → 改用「**主实验用 b16、部署验收用 lite**」的两档叙事，`docs/09` 已经把这条结论写好了，论文可单独一节讲「体积-精度权衡」。

### P1 卡时账（实测重算，不再估算）

实测节奏：stage1 **384 s/epoch**、stage2 **440 s/epoch**、stage3 **471 s/epoch**；
09-28 那次 55 轮 = 430 分钟。

> **一次 b16 完整训练（含早停）≈ 7.2 h；跑满 70 轮 ≈ 9 h。**

- P1-a 一次 (9 h) + P1-c lite 一次 (≈3 h，参数量 1/3.7) + 评测 (1 h) ≈ **13 h ≈ ¥25**
- 若 P1-b 也跑 → 再加 9 h ≈ **¥42**
