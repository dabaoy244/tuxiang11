## 〇、开工前必须先修的两个「静默失效」

这两条不在原计划里，但不修的话 P0 跑出来的**所有数字都是废的**。

### 0.1 本机缺 CLIP 预训练骨干 → 权重静默错配

`CLIPViTBackbone` 在找不到 `pretrained/clip-vit-base-patch16`、也没有 HF 缓存时，
会静默回退到 `TinyViTFallback`（另一套实现、另一套键名）。后果：

```
load_state_dict(..., strict=False)
  → missing 150 / unexpected 199
```

`strict=False` 把不匹配的键**静默吞掉**，于是**整个空域骨干（85.8M 参数）保持随机初始化**，
脚本照常跑完、报告照常生成，只是指标变成了 ACC 0.5000、三种 mIoU 全 0.0000。

**判据（一行就能看出来）**：日志里应当出现
`[CLIPViTBackbone] 冻结前 6/12 层，可训练参数 42.53M / 85.80M`；
若出现 `兜底骨干：不做层冻结` 就是踩了这个坑。

**修法**：补齐 `pretrained/clip-vit-base-patch16`。本机直连 huggingface.co 超时，
但 **hf-mirror.com 可达**：

```bash
export HF_ENDPOINT=https://hf-mirror.com HF_HUB_DISABLE_XET=1
python -c "from huggingface_hub import snapshot_download; \
  snapshot_download('openai/clip-vit-base-patch16', \
  local_dir='pretrained/clip-vit-base-patch16', \
  allow_patterns=['*.json','model.safetensors','pytorch_model.bin'])"
```

### 0.2 transformers ≥5 改了键名布局 → 又一个静默错配

transformers 5.x 去掉了 `CLIPVisionModel → vision_model` 这层嵌套，键名从
`vision_model.embeddings.*` 变成 `embeddings.*`。权重内容没变，只是少一层前缀，
于是**云端（4.x）训出的 checkpoint 在 5.x 上加载会再次 150/199 错配**。

**修法**（已改入代码，见 `src/models/spatial_branch.py::_CLIPVisionV4Layout`）：
在 `_load_clip` 返回前补一层 `vision_model` 包装，两边通用，无需降级 transformers。

修完后：**missing 0 / unexpected 0，401 个键全部对上**，
且日志与云端逐字一致（`冻结前 6/12 层，可训练参数 42.53M / 85.80M`）。

## 一、P0-① 定位归因诊断 ★（已跑完）

**做了什么**：在现有权重上，按 GT 篡改面积把 CASIAv2 test 的 513 张篡改图分 6 桶，
逐图算 IoU（= `miou_tampered_only` 的口径），并统计每桶的像素召回/精度。

**脚本**：`scripts/diag_area_buckets.py`（新增）
**产物**：`outputs/diag/diag_area_buckets.md`、`outputs/diag/diag_area_buckets.json`
**耗时**：512 s（本机 CPU，1263 张，约 2.5 张/秒）

### 1.1 先看口径复现：本地与云端**逐位一致**

| 口径 | 本机实测 | 云端 `eval_casia.json` |
|---|---|---|
| ★ `miou_tampered_only` | **0.2668** | 0.2668 |
| 池化 `miou` | 0.4570 | 0.4570 |
| 逐图 `miou_per_sample` | 0.2525 | 0.2525 |
| Pixel Acc | 0.9748 | 0.9748 |
| Dice | 0.6273 | 0.6273 |
| ACC / F1 / AUC | 0.9382 / 0.9259 / 0.9847 | 0.9382 / 0.9259 / 0.9847 |

> 这不是"又一个评测"，而是对云端那次评测的**独立复现**：
> 换机器、换代码路径（本地 CPU + 显式指定权重）后数字完全相同，
> 说明 09-28 的结果不是环境或流水线偶然产物。**论文里可以写这一条。**

### 1.2 ★ 分桶结果（核心证据）

| GT 篡改面积桶 | n | 逐图 IoU ★ | 池化 IoU | 像素召回 | 像素精度 | 预测面积/GT | IoU≥0.1 |
|---|---|---|---|---|---|---|---|
| ≤0.5%（极小） | 65 | **0.0461** | 0.0337 | 0.131 | 0.096 | 3.32 | 13.8% |
| 0.5%~2%（小） | 145 | **0.1436** | 0.1218 | 0.243 | 0.273 | 1.51 | 33.8% |
| 2%~5%（中小） | 106 | **0.1681** | 0.1546 | 0.255 | 0.322 | 1.03 | 40.6% |
| 5%~10%（中） | 82 | **0.3592** | 0.3592 | 0.496 | 0.562 | 0.95 | 72.0% |
| 10%~25%（大） | 63 | **0.5034** | 0.4686 | 0.612 | 0.697 | 0.92 | 81.0% |
| >25%（极大） | 52 | **0.6550** | 0.6230 | 0.735 | 0.845 | 0.89 | 88.5% |

**IoU 随篡改面积单调递增，跨度超过 14 倍**（0.046 → 0.655）。

### 1.3 归因判定

| 现象 | 实测 |
|---|---|
| 小面积桶（≤2%，n=210）逐图 IoU | **0.1134** |
| 大面积桶（>10%，n=115）逐图 IoU | **0.5720** |
| 全体（n=513） | 0.2668 |

**→ 归因：小目标被压掉，不是定位头整体不会定位。**

关键的一点：**≤2% 的图占了 513 张里的 210 张（41%）**，
把它们单独拿出来是 0.1134，剩下的 303 张是 **0.373** ——
也就是说，**单是这 41% 的极小篡改图，就把 0.373 拉到了 0.2668。**

而"预测面积/GT 面积"这一列还揭示了第二层问题：

- ≤0.5% 桶 = **3.32**：预测面积是 GT 的 3.3 倍，但像素召回只有 0.131
  → 不是"缩着不敢预测"，而是**预测位置偏了**（撒了一大片、却基本没盖住目标）。
  224 输入下 0.5% ≈ 500 像素（约 22×22），定位头在这个尺度上已无法分辨边界。
- >10% 桶 ≈ 0.9：大面积下**轻度欠分割**，属正常范围。

### 1.4 真实图误报

750 张真实图中，**2.9%** 预测出超过 0.5% 面积的"篡改区域"，平均预测面积占比 0.0011。
→ 定位支路的假阳性**不是当前主要矛盾**，暂时不用动。

### 1.5 对 P1 的直接结论

按 `docs/20` §四的分支，本次实测**明确落在"小目标"这一支**，因此：

| 优先级 | 改动 | 理由（来自本诊断） |
|---|---|---|
| ★ 1 | 输入 224 → **320** | 小区域像素数 ×2（0.5% 从 ~22² 变 ~31²），直接对症 |
| 2 | 定位头输出层上采样到更高分辨率 | 弥补 14×14 瓶颈；与提分辨率可叠加 |
| 3 | 边缘损失权重上调 | 改善 2%~10% 桶的边界（该区间召回 0.26~0.50，最像"边界不准"） |

**反过来，`refine_channels` 32→64 的优先级应当下调** ——
那是"定位头容量不足"的对策，而实测显示大面积桶已经有 0.50~0.66，
容量不是瓶颈，**分辨率才是**。

> ⚠ 期望管理：提分辨率**救不回 ≤0.5% 那一档**（65 张、IoU 0.046）。
> 现实目标是把 0.5%~5% 这两档（251 张）从 0.15 拉到 0.4 量级，
> 全体因此从 0.2668 上到 **0.35~0.40**；要到 0.56 需要更大的结构性改动。

## 二、P0-② CPU 吞吐重测 —— ✅ **达标；此前的"不达标"是线程超订造成的假象**

**做了什么**：把 09-28 的 b16 权重导出 ONNX（`deploy/b16_20260928.onnx`，**363.3 MB**，
opset 17，`onnx.checker` 与 onnxruntime 推理均通过），连同 lite 档一起跑
`scripts/benchmark_cpu.py`（5 轮 × 20 次，取中位数）。

### 2.1 第一轮（关掉 douyin / quark 后，负载 686% → 162%）

| 模型 | 体积 | 中位延迟 | 中位吞吐 | 逐轮延迟（ms） | 轮间波动 |
|---|---|---|---|---|---|
| `b16_20260928.onnx` | 363.3 MB | 312.7 ms | 3.20 张/秒 | 312.7/248.5/280.8/400.6/344.0 | 61% |
| `lite_simplified.onnx` | 98.7 MB | 147.6 ms | **6.77 张/秒** ✗ | 151.0/182.7/147.6/125.2/129.7 | 46% |
| `lite.onnx` | 99.2 MB | 160.1 ms | 6.25 张/秒 | 142.8/160.1/151.4/168.0/207.8 | 46% |

关掉常驻程序确实快了一倍（5.54 → 6.77），**但仍达不到 9/17 那次的 9.46**，
而且轮间波动仍有 46%。说明还有一个与"别的程序"无关的变量。

### 2.2 ★ 真因：ORT 默认用满全部逻辑核 ⇒ **线程超订**

`benchmark_cpu.py` 此前不传 `--threads` 时 `intra_op_num_threads` 留空，
ONNX Runtime 就按逻辑核数（7）开 intra-op 线程。逐档扫（**同一文件、同一台机器、
同一次会话内连续测**，`lite_simplified.onnx`）：

| intra-op 线程数 | 中位延迟 | 中位吞吐 | 轮间波动 | 判定 |
|---|---|---|---|---|
| 2 | 117.4 ms | 8.52 张/秒 | 2% | ✅ |
| 3 | 92.9 ms | 10.77 张/秒 | 4% | ✅ |
| **4** | **85.3 ms** | **11.73 张/秒** | **10%** | ✅ ★ 最优 |
| 5 | 90.7 ms | 11.03 张/秒 | 21% | ✅ |
| 6 | 99.9 ms | 10.01 张/秒 | 72% | ✅ |
| **7（= 此前所谓"默认"）** | 147.6 ms | **6.77 张/秒** | 46% | ❌ |

复测确认（第二遍）：`lite_simplified` @4 = **10.98** 张/秒，`lite` @4 = **11.74** 张/秒。

**关键对照：连 9/17 那次"空载"的全核结果（105.7 ms / 9.46 张/秒）也不如今天固定
4 线程的 85.3 ms / 11.73 张/秒。** 也就是说，用满核**在任何负载下都不是最优** ——
7 个 intra-op 线程把 7 个逻辑核占满，连 OS 自身和 spin-wait 空转都要挤，
线程反而互相抢占。留出余量（4 线程）既更快又更稳。

> 这也解释了为什么此前的数字会让人误判：**全核档只在"机器极度安静"时才接近它自己
> 的上限，一旦有任何其它负载就崩到 6.77 并剧烈抖动**。这正是"看起来像模型不行、
> 其实是测量配置不行"的典型。

### 2.3 ✅ 结论：CPU ≥8 张/秒**达标**

| 口径 | 数字 | 目标 | 判定 |
|---|---|---|---|
| `lite_simplified.onnx`（98.7 MB）@ threads=4 | **11.73 张/秒**（复测 10.98） | ≥8 | ✅ **达标，约 1.47 倍余量** |
| `lite.onnx`（99.2 MB）@ threads=4 | 11.74 张/秒 | ≥8 | ✅ |
| `b16_20260928.onnx`（363.3 MB）@ threads=4 | 4.92 张/秒 | ≥8 | ✗（体积也不达标） |

→ **体积与 CPU 两项硬指标由同一个动作解决：部署/验收用 lite 档（s16）。**
b16 只作研究主模型，不用于 CPU 实时路径 —— 这与 `docs/09` 的两档叙事一致。

### 2.4 顺带修掉的两个真实缺陷（不只是改文档）

**① 交付的桌面工具本来跑在最差档上。**
`src/deploy/inference.py::_init_onnx` 此前是
`ort.InferenceSession(path, providers=providers)` —— **完全没有 SessionOptions**，
即 ORT 全核默认。也就是说 exe 演示时的吞吐一直是 6.77 那一档。
已改为显式设线程数，并抽出 `ort_num_threads()`（默认 `min(4, 核数)`，
可用环境变量 `VIBNET_ORT_THREADS` 覆盖）。

**② 基准脚本的"默认"就是最差档。**
`scripts/benchmark_cpu.py` 的 `--threads 0` 也已改为走 `ort_num_threads()`，
保证**基准与线上用同一套线程策略**。改后实测：不传 `--threads` 时
自动取 4，得到 87.5 ms / **11.42 张/秒**，`meets_cpu_8fps=True`。

（`src/deploy/quantize_int8.py` 里同一处 `os.cpu_count()` 全核写法也一并修了。）

### 2.5 仍需注意的两点

1. **验收要按 4 线程口径测，且现场演示前关掉浏览器/播放器。**
   全核档的余量是假的；固定 4 线程后余量 1.47 倍、波动 10%，是健康的。
   答辩前先在**演示机**上标定一次线程数（`--threads N` 各测一遍取最优）。
2. **本机 CPU 无 VNNI 再次被证实**：`lite_int8.onnx` 体积降到 25.7 MB，
   吞吐反而只有 1.54~3.35 张/秒。→ INT8 **只省体积、不省时间**，`docs/09` 的结论成立。

### 3.2 ⚠ 两个必须先纠正的口径

**① `progan` 子集不是泛化测试，它在抬高宏平均。**

`ForenSynths/train` 的伪造图**只有 ProGAN**（见 `src/data/datasets.py` 目录说明），
而 `test` 里含 `progan` 子集 —— 与训练集**同生成器**。它的 ACC 是 **1.0000**（满分）。

**排除 progan 后，严格跨生成器宏平均 ACC = 0.6667**（真图 0.4250 / 假图 0.9083）。
论文里两个数都要报，并注明差别来自"progan 是已见生成器"。

**佐证（三条独立证据互相印证）**：训练时 val（= ProGAN 保留集）的
`val_cls_auc = 0.9991` 饱和 → test/progan ACC = 1.0000 → test 其余生成器 AUC 只 0.59~0.93。
三条都指向同一件事：**模型学到的是 ProGAN 特有的线索，不是通用的"生成痕迹"**。

**② 真图基本识别不出来。** 真图 ACC 宏平均只有 **0.4692**，
假图 0.9154 —— 模型系统性偏向判"伪造"。这解释了 09-28 评测 A 里
Precision 仅 0.6905（41.2% 真实图被误报为伪造）的现象，是同一病灶。

### 3.3 ★ 塌缩诊断：不是阈值问题，是表示塌缩

|---|---|---|---|---|

| 严格跨生成器（乐观） | 0.6667 | 0.9999 | 0.7636 | +0.097 |
| 严格跨生成器（**半劈 holdout，诚实**） | 0.6667 | 0.990 | **0.6963** | **+0.0297** |

→ **只能白拿 +0.03，远不足以救 91%。** 原因看分数分布就清楚了：

> ⚠ **P1 的改法要调整**：`docs/20` §四原计划是"定位攻坚 + lite 骨干"。
> 按本次实测，**下一轮训练第一优先应是"扩生成器多样性 + 换 cross-gen val"**，
> 定位分辨率列为第二优先 —— 否则 91% 那条永远无解。

## 四、P0-⑥ 验证集重构（方案 B）—— 已实现并验收

**问题**：原 val = `ForenSynths/val`(8000, ProGAN) + `CASIAv2/val`(1261)，与 train 同生成器
⇒ `val_cls_auc` 在 epoch 13 就到 **0.9995** 饱和、失去区分度 ⇒ **`best.pt` 的挑选依据失效**。
P0-④ 又证明了同一病灶的另一面：模型只学到 ProGAN 线索，跨生成器直接塌缩。

### 4.1 落地内容

**方案 B（整个留出生成器）**，落成 `configs/default_crossval.yaml`：

| 项 | 内容 |
|---|---|
| val_cross | `ForenSynths/test` 的 **biggan / cyclegan / stargan**，`max_per_generator: 400` ⇒ **2400 张**（真/假各 1200） |
| val 其余成分 | `CASIAv2/val`（1261，给定位支路的 `val_loc_miou` 提供掩码）+ `COVERAGE/val` |
| test | `exclude_generators: [biggan, cyclegan, stargan]` ⇒ 79689 张，协议从 13 生成器变 **10 个** |

**为表达它而加的能力**（`src/data/datasets.py`）：`GenSynthsDataset` 新增
`include_generators` / `exclude_generators` / `max_per_generator`，
`build_dataloaders()` 同步透传；`scripts/eval_cross_generator.py` 新增
`--generators` / `--exclude-generators`。

★ **都带反静默失效校验**：生成器名拼错、或对**不含生成器层级**的 split（如
`ForenSynths/val`，第一层是 `airplane` 这类物体类别名）施加筛选，一律**直接抛错**
并列出盘上实际存在的名字 —— 而不是静默筛出个小集合，让指标在一个意外的子集上算出来。
（已实测：`include=['style_gan']` 与对 `split=val` 筛选，两条都被拦下。）

**核对过的隐患**：val_cross 的真图与其余生成器的真图**文件名交集 = 0**
（5319 vs 20902）⇒ 二者真图不重叠，不存在 val↔test 的真图泄漏。

### 4.2 验收结果（实测，本机 CPU 843 s）

| 生成器 | n（真/假） | ACC | 真图 ACC | 假图 ACC | AUC | AP |
|---|---|---|---|---|---|---|
| biggan | 400/400 | 0.6800 | 0.3625 | 0.9975 | 0.9268 | 0.9127 |
| cyclegan | 400/400 | 0.5150 | **0.0300** | 1.0000 | 0.8739 | 0.8300 |
| stargan | 400/400 | 0.7612 | 0.5225 | 1.0000 | 0.9974 | 0.9973 |
| **宏平均** | 2400 | **0.6521** | 0.3050 | 0.9992 | **0.9327** | 0.9133 |
| 微平均（池化） | 2400 | 0.6521 | 0.3050 | 0.9992 | **0.9137** | 0.8765 |

**验收判据（AUC 脱离饱和）= 通过：0.9981 → 0.9137（池化）/ 0.9327（宏平均）。**

→ val 重新具备区分度，`best.pt` 的挑选依据恢复有效。**P1 可以开跑。**

> ⚠ 注意 ACC 只有 **0.6521**，比测试集的 0.6696 还低。这不是矛盾：biggan / cyclegan
> 是"AUC 尚可但阈值严重偏"的生成器（真图 ACC 0.36 / 0.03，而 AUC 0.93 / 0.87）。
> 即 **val 上的操作点很差，但排序能力还在** —— 而早停用的正是 AUC，所以不受影响。
> 但也再次印证 P0-④ §3.3 的塌缩诊断：**真图被系统性判成伪造**。

### 4.3 ★ 残余偏差：这组留出的生成器"偏容易"

用已有 `outputs/cross_gen_20260928/scores.npz`（13 生成器各 300 张）算逐生成器 AUC：

| 生成器 | AUC | 生成器 | AUC |
|---|---|---|---|
| progan（=训练同源） | 1.0000 | imle | 0.8242 |
| stylegan | 0.9986 | whichfaceisreal | 0.8204 |
| **stargan** ⟵ 留出 | 0.9963 | crn | 0.8030 |
| stylegan2 | 0.9840 | deepfake | 0.7842 |
| **biggan** ⟵ 留出 | 0.9274 | san | **0.5901** |
| gaugan | 0.9143 | | |
| **cyclegan** ⟵ 留出 | 0.8940 | | |
| seeingdark | 0.8717 | | |

- 12 个未见生成器的宏平均 AUC = **0.8673**
- 留出的 3 个 = **0.9392**；剩下的 9 个（= 现在报的测试集）= **0.8434**
- **⇒ val（0.93）比 test（0.84）容易，差约 0.09。**

**这个偏差的方向是"保守"的**，两点：

1. 留出的恰好是**偏容易**的生成器 ⇒ 测试集**变难**（0.8673 → 0.8434），
   所以我们报的测试数字**偏低而非被美化**；
2. val 比 test 容易 ⇒ 早停信号偏乐观 ⇒ 最终测试表现只会**比 val 更差**，不会更好。

#### ⚠ 一个必须说清的更正：换 val 并没有缩小 val–test 的"差距量级"

我一度写过"差距减半"，那是**错的** —— 它拿旧 val 的 0.9981（混合 val，含 CASIAv2）
去减 0.8350（纯 ForenSynths 池化），两个口径不同源、不能相减。按**同源同指标**重算：

| 口径 | 旧（`default.yaml`） | 新（`default_crossval.yaml`） |
|---|---|---|
| val AUC（纯 ForenSynths 部分） | **1.0000**（`progan` 保留集，饱和） | **0.9327** 宏 / 0.9137 池（val_cross 实测） |
| test AUC（同源池化 / 宏平均） | 0.8581 / 0.8776（13 生成器） | 0.8211 / 0.8434（10 生成器） |
| **val − test** | **+0.1224**（宏，且 val 区分度 = 0） | **+0.0893**（宏） |

**所以换 val 真正修好的是"饱和"，不是"差距量级"**：
旧 val 的 AUC 是 1.0000（连一个 checkpoint 都排不出来，早停实际是随机停的），
新 val 是 0.9327（有真实区分度）。差距从 0.122 降到 0.089，只收缩了约 1/4。
**残余的 0.09 是"留出的这 3 个生成器偏容易"造成的选择偏差**，可以再修（见下表），
但不修也已不影响早停的有效性。

**若要把偏差也消掉，有两条路（都留到 P1/论文阶段决定）：**

| 做法 | 效果（用 `scores.npz` 同口径估算） | 代价 / 风险 |
|---|---|---|
| ① 换成"难度匹配"的留出三元组：`biggan + cyclegan + deepfake` | val 宏 0.8685 / 池 0.8391；test 宏 0.8669 / 池 0.8504 → **val−test 宏差 0.0016**（现在 0.0893） | 改一行配置。**但要注意副作用**：test 会因为留下 `stargan`/`stylegan`（易）而去掉 `deepfake`（难），报告的宏平均从 0.8434 升到 0.8669 —— 它**更接近全体 12 生成器的均值 0.8673**（即更"代表性"），但绝对数字是变好看的，容易被质疑 |
| ② **分层抽样留出**：每个未见生成器各抽 N 张作 val，并从 test 精确排除这批图 | val 与 test **都**是全体 12 生成器的分层子集 ⇒ 两边难度**按构造**都 ≈ 0.8673，且没有任何生成器被剔出测试 | 最严，且能同时修好"val 不代表 test"和"test 不代表全体"两个问题；代价是要给 `build_dataloaders` 加"按路径清单排除"的能力（`eval_cross_generator.py` 已有 `--exclude-list`，数据集侧还没有） |

> **建议**：**P1 先按现状跑**（`biggan/cyclegan/stargan`，已实测验收、偏差方向保守、
> test 数字偏低不虚高），把这条偏差作为**已知限制**写进中期材料；
> **论文定稿前再上 ②** —— 它才能同时消掉两个代表性偏差，而 ① 只是把偏差从
> "val 偏易"换成"test 偏易"。

**另有一处已知损失**：被留出的 3 个生成器只用了 400/生成器，剩余约 8.2k 张图
既不在 val 也不在 test。若要利用它们，把 `max_per_generator` 调大或去掉即可
（val 会变成 10640 张，云端每轮评测成本上升，但在 4090 上可忽略）。
